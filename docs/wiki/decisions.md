- 반영: 로컬 `ramap-architecture`, `ramap-module-structure`, `ramap-design-patterns` 스킬, [아키텍처](engineering.md), [모듈 구조](engineering.md), [디자인시스템](engineering.md), [승격한 후보](inbox/source-alignment.md).

- 대체한 결정: 없음. DEC-0001의 스킬 소유권 원칙을 유지하며 초기 후보를 해소합니다.

## DEC-0003 프로필·리뷰 이미지 URL 기본 배치 발급 채택

- 기록일: 2026-10-12 (Asia/Seoul).
- 결정: 프로필·리뷰 이미지 URL은 Supabase Storage 기본 배치 API로 발급합니다. 앱 발급 경로는 Edge Function과 Redis에 의존하지 않으며 호출자의 JWT와 기존 Storage RLS 검사를 사용합니다.
- 이유: 검토 후 사용자가 기본 배치 방식을 선택했습니다. 이 경로는 별도 캐시 서비스 없이 여러 경로를 한 요청으로 묶으면서 기존 권한 검사를 유지합니다.
- 근거: 사용자의 기본 배치 방식 선택 및 적용 요청.
- 반영: [이미지 URL 구현](backend.md), [백엔드 탐색](backend.md), 공통 데이터 소스와 회귀 테스트.
- 적용 상태: 앱 코드에 적용했습니다. 이 기록만으로 앱 릴리스나 운영 성능 개선을 주장하지 않습니다.
- 대체한 결정: 없음.

## DEC-0007 내 리뷰 상세 닫기에서 목록 재조회 제외

- 기록일: 2026-10-12 (Asia/Seoul).
- 결정: 내 리뷰에서 매장 상세를 변경 없이 닫을 때는 리뷰 목록을 다시 조회하지 않습니다. 상세에서 본인 리뷰를 삭제하면 해당 항목과 집계를 현재 목록 상태에 반영하고, 리뷰 작성·수정 화면에서 복귀할 때는 기존 목록 갱신 동작을 유지합니다.
- 이유: 단순 상세 열람은 리뷰 목록을 바꾸지 않으며, 재조회하면 새 서명 이미지 URL로 인해 기존 리뷰 사진까지 다시 로드됩니다.
- 근거: 사용자가 상세를 열고 닫을 때 전체 리뷰 이미지가 갱신되는 현상을 보고하고, 단순 닫기 시 재조회를 제외하는 수정에 동의했습니다.
- 반영: [제품 정책](product-policy.md), [앱 실행 흐름](app-flows.md#리뷰-작성저장복귀), [MyReviewsRoute](../../feature/review/my/src/commonMain/kotlin/com/peto/ramap/ui/review/my/MyReviewsRoute.kt).
- 적용 상태: 구현은 검증된 PR 코드 커밋 `c559e52c3248076dacab2f2928622d9d787bc1e5`에 반영됐습니다. 닫기·복귀 경로의 실기기 확인은 이전 `1.1.9-debug` APK 기준이며, 최종 dialog 포함 코드를 기기에 재설치한 결과는 아닙니다. 스토어 앱 릴리스를 뜻하지 않습니다.
- 대체한 결정: 없음.

## DEC-0008 리뷰 변경 기록으로 화면 동기화

- 기록일: 2026-10-12 (Asia/Seoul).
- 결정: 성공한 리뷰 변경은 repository가 한 번 발행하고 화면·상세 캐시가 cursor로 적용합니다. 세션 전환은 기록을 초기화하고 접근 변경·기록 공백은 필요한 조회를 복구합니다. passive 복귀는 리뷰 조회·서명을 시작하지 않습니다.
- 이유: 중첩 작성·수정·삭제의 부모 목록 누락과 전체 이미지 재로딩을 함께 해결하고 페이지·필터·스크롤을 유지합니다.
- 근거: 사용자가 공통 ReviewChangeStore revision journal 방식을 승인하고, 정상 변경마다 전체 목록을 조회하지 않도록 요청했습니다.
- 반영: [설계 패턴](app-flows.md#리뷰-작성저장복귀), [실행 흐름](app-flows.md#리뷰-작성저장복귀), [제품 정책](product-policy.md), [백엔드](backend.md).
- 적용 상태: 앱 구현은 검증된 PR 코드 커밋 `c559e52c3248076dacab2f2928622d9d787bc1e5`에 반영됐으며 앱 스토어에는 배포하지 않았습니다. 리뷰 v2 RPC는 2026-10-13에 migration `20261012151044`로 운영 배포됐고 기존 UUID v1 API를 유지합니다. 메타데이터 보완 이후 domain 126 + data 145 + MyReviews feature 8, 총 279개 Android host test가 통과했습니다. 이 279건에는 OtherReviews 테스트가 포함되지 않습니다. 이전 463개 host test와 10개 모듈 lint·debug APK·iOS framework 결과는 메타데이터 보완 전 코드 기준입니다. Android 16 실기기에서는 리뷰 목록 복귀·상태·v2 임시 쓰기·사진 교체·계정 전환과 새 리뷰 매장 요약 첫 렌더를 이전 `1.1.9-debug` APK에서 확인했습니다. 최종 코드 그룹 1–9의 branch check는 모두 exit 0이며 `compileAndroidHostTest` 작업은 테스트 코드를 컴파일했지만 실행하지 않았습니다. PR9 코드에서는 Android APK, iOS Simulator framework 및 관련 lint도 통과했습니다. 상세 한계는 [백엔드](backend.md)와 [이미지 URL](backend.md)에 기록합니다.
- 대체한 결정: [DEC-0007](#dec-0007-내-리뷰-상세-닫기에서-목록-재조회-제외).

## DEC-0009 위키 갱신 시점

- 반영: [유지보수 정책](maintenance.md), [PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE.md).
- 적용 상태: 이 문서와 PR template, repository instructions/skills에 procedure가 반영됐습니다. 구현 규칙은 소유 Ramap 스킬에 유지합니다.

- 이유: 매장 단위로 미래 공지를 숨기거나 상세에 모든 날짜를 섞으면 방문하려는 날짜의 영업 여부를 구분하기 어렵습니다.
- 승인 근거: 사용자가 오늘·예정 공지가 분리되지 않는 화면을 제시하고, 같은 매장을 두 탭에 각각 표시하며 상세도 선택 날짜의 공지만 표시하는 방식을 선택했습니다. 앞서 예정은 날짜별로 정렬하고 빈 날짜를 생략하도록 요청했습니다.
- 적용 범위: 새소식 영업 변동의 날짜별 목록, 탭 집계, 공지 상세. 원본 공지 날짜와 본문 및 정규 영업시간은 변경하지 않습니다.
- 대체한 결정: DEC-0019 중 오늘 매장을 예정에서 제외하고 모든 관련 날짜의 공지를 한 상세에 모으던 목록·상세 기준을 대체합니다. 세 유형 정의와 영업 상태 적용 기준은 유지합니다.
- 반영: [제품 정책](product-policy.md#이벤트와-영업-변경), [도메인 용어](domain.md#이벤트와-영업시간).
- 적용 범위: 관리자·수동 등록과 사용자에게 공개되는 영업 공지 및 영업 상태 표시. 정확한 시각이 없는 원문만으로 마감 시각을 자동 추정하지 않습니다.
- 대체한 결정: 없음. 기존 날짜별 일반 변경·오픈 지연을 제공하던 공지 범위를 두 유형으로 제한합니다.

## DEC-0021 진행 중인 기간 공지의 전체 일정 표시

- 기록일: 2026-10-18 (Asia/Seoul).
- 결정: 종료일이 정해진 여러 날의 기간 공지가 종료되기 전에는 예정 목록의 시작일부터 종료일까지 모든 날짜에 표시합니다. 오늘 이전 날짜와 오늘을 잘라내지 않습니다. 오늘 탭의 당일 공지 표시, 날짜별 상세와 고유 매장 수 집계는 유지합니다.
- 이유: 기간 공지의 일부 날짜만 표시하면 공지가 적용되는 전체 일정을 확인할 수 없습니다.
- 승인 근거: 사용자가 진행 중인 기간 휴무를 시작일부터 종료일까지 모든 날짜 구간에 표시하도록 명시했습니다.
- 적용 범위: 새소식의 기간 공지 일정 표시. 월간 달력의 개별 휴무일을 명시하지 않은 날짜까지 확장하지 않습니다.
- 대체한 결정: DEC-0020의 미래 날짜만 표시하는 기준에 기간 공지의 전체 일정 표시 예외를 추가합니다. 단일 날짜 공지와 달력 공지의 날짜 기준은 유지합니다.
- 반영: [제품 정책](product-policy.md#이벤트와-영업-변경).

## DEC-0022 Git·PR을 기본 작업 기록으로 사용

- 기록일: 2026-10-18 (Asia/Seoul).
- 결정: 코드·문서 변경은 Git과 PR의 공유 이력으로 관리합니다. 테스트·검증 결과는 PR 또는 CI 기록에, 배포 상태는 관련 PR·배포 기록에 남깁니다. 로컬 전용 `docs/change-history/CHANGELOG.md`의 새 작업별 기록은 중단하며, 기존 파일은 과거 기록 보관용으로 유지합니다.
- 이유: Git·PR의 공유 변경 이력과 별도로 checkout 간 공유되지 않는 로컬 작업 로그를 매 수정마다 유지하면 중복과 누락이 생깁니다. 검증과 배포 근거를 해당 변경·배포 기록 가까이에 두어 확인 경로를 명확히 합니다.
- 승인 근거: 사용자가 Git 추적 이력과 중복되는 로컬 변경 기록을 제거하는 방향을 승인했습니다.
- 반영: `AGENTS.md`, `ramap-coding-conventions` 스킬, [위키 유지보수 규칙](maintenance.md), [개발 참고](engineering.md), [백엔드 변경 기록](backend.md), [PR 템플릿](../../.github/PULL_REQUEST_TEMPLATE.md).
- 적용 범위: 새 수정 작업의 기록 절차입니다. 기존 로컬 로그와 별도 보안·운영 증거는 공유 범위를 바꾸지 않습니다. 위키 의미 변경 검토 시점과 정책·도메인 지식 갱신 기준은 유지합니다.
- 대체한 결정: DEC-0014와 DEC-0009의 로컬 변경 이력 보관 절차. DEC-0009의 최종 PR 위키 검토 시점은 유지합니다.

## DEC-0023 새소식·이벤트 사용자 제보 제거

- 기록일: 2026-10-18 (Asia/Seoul).
- 결정: 신메뉴·리뉴얼·이벤트 URL·사진 제보 제출 흐름을 제거합니다. 새소식 목록은 이벤트 유형 필터 없이 등록된 이벤트를 함께 보여줍니다.
- 이유: 사용자가 해당 유형을 제보하는 기능을 제거하도록 요청했습니다.
- 승인 근거: 사용자의 “신메뉴, 리뉴얼, 이벤트 제보하기 기능제거” 요청과 후속 “아니 일단 관리자는 건들지마” 범위 지정.
- 적용 범위: 사용자 제보 화면·앱 API·새소식 제보 RPC·목록 유형 필터. 기존 이벤트와 제보 자료는 보존하며, 관리자 등록 동작과 제보 사진 접근 정책은 변경하지 않습니다.
- 반영: [제품 정책](product-policy.md#제보-사진), [이벤트 정책](product-policy.md#이벤트와-영업-변경), [기능과 도메인](feature-map.md), [사용자 흐름](app-flows.md#이벤트와-알림).
- 대체한 결정: DEC-0016의 URL만 제출하는 제보 허용 문장만 대체합니다. 제보 사진 열람·삭제 조건은 유지합니다.

## DEC-0024 매장명 우선 검색과 지역·장소 탐색

- 기록일: 2026-10-22 (Asia/Seoul).
- 결정: 공백을 정규화한 연속 일치로 매장명을 우선 검색하고, 동일 관련도 안에서는 전체 거리순으로 정렬한 뒤 결과 수를 제한합니다. 지역·장소 후보를 함께 제공하며 정상 조회 결과가 장소 하나뿐이면 바로 이동합니다. 다른 경우에는 사용자가 선택한 목적지 주변의 등록 매장을 탐색합니다. 매장과 장소 결과가 함께 있으면 매장 목록 위 지도에 작은 장소 바로가기를 유지합니다.
- 이유: 글자 사이의 임의 내용을 허용하면 다른 행정구역의 주소가 일치할 수 있고, 지역·도로명·매장명에 같은 단어가 있어도 탐색 의도는 다릅니다. 매장 결과의 유무만으로 장소 검색을 생략하면 원하는 지역으로 이동할 수 없습니다. 장소 바로가기를 목록과 분리하면 매장 결과가 많아도 지역 이동 경로를 찾을 수 있고, 매장 목록의 공간과 정렬을 유지할 수 있습니다.
- 승인 근거: 사용자가 매장명 우선, 정규화, 거리 정렬과 지역·장소 검색을 포함한 개선 계획을 승인하고 구현을 요청했습니다. 이후 성남시청·야탑역처럼 결과가 장소 하나뿐이면 바로 이동하도록 추가 요청했으며, 검색 결과 배치 프로토타입에서 작은 바로가기를 선택했습니다. 전수 검사에서 발견된 장소 오매칭, 지역·상호 복합 검색 누락과 한 글자·긴 상호 입력 문제의 수정을 요청했습니다.
- 적용 범위: 한국 지도 검색과 장소 선택 후 주변 탐색. 매장 제보의 URL 중복 확인과 영업 변동 목록의 검색은 유지합니다.
- 반영: [제품 정책](product-policy.md#지도와-검색), [사용자 흐름](app-flows.md#지도-검색과-상세).
