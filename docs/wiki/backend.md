# 운영·보안 규칙

이 문서는 운영에서 지켜야 할 정보 공개와 신뢰 경계를 설명합니다. 실시간 서버 상태표나 배포 이력은 아닙니다. 접근 권한을 수정할 때는 기존 규칙과 실제 서버 동작을 함께 확인합니다.

## 역할과 신뢰 경계

| 역할 | 권한을 판단할 때 확인할 것 |
| --- | --- |
| 비회원 | 공개 정보와 해당 기능에서 허용한 익명 입력만 이용합니다. |
| 로그인한 회원 | 로그인 여부에 더해 본인 소유권·공개 범위·차단 등 행동별 조건을 확인합니다. |
| 관리자 | 회원이 직접 변경할 수 없는 서버 측 관리자 등록으로 확인합니다. |
| 신뢰된 서버·수집 작업 | 일반 회원에게 공개하지 않는 자료와 내부 처리를 담당합니다. |

이메일 기본값이나 회원이 편집할 수 있는 프로필 metadata만으로 관리자 권한을 부여하지 않습니다. 관리자에게 허용된 API라고 해서 모든 역할에 실행 권한을 열지 않습니다.

## 기기의 로그인 세션

| 상황 | 세션 처리 |
| --- | --- |
| 기기에 저장 | 기기의 보안 저장 기능으로 보호하고, 인증 데이터는 일반 백업과 기기 이전에서 제외합니다. |
| 기존 설치 업데이트 | 새 저장소에 세션을 저장한 뒤 이전 값을 정리합니다. 이관에 실패하면 기존 값을 보존합니다. |
| 로그아웃 | 이전 저장소에 값이 남아 있어도 세션을 복원하지 않습니다. |
| 키 유실 또는 데이터 손상 | 복구할 수 없으면 다시 로그인하도록 처리합니다. 일시적인 저장소 접근 오류가 발생하면 기존 세션을 보존합니다. |

## 공개 정보와 내부 정보

| 대상 | 공개 범위 |
| --- | --- |
| 매장 | 서비스에서 비공개로 설정한 매장은 공개 조회에서 제외합니다. |
| 영업 공지 | 공지에 필요한 정보만 공개합니다. OCR 원문과 검수 자료는 내부에 둡니다. |
| 영업 상태 | 매장 식별자·상태·확인 시점을 공개합니다. 수집 원천·오류·재시도·다음 수집 일정은 서버에서만 확인합니다. |
| 프로필·리뷰·저장 목록 | 비공개 계정에서도 닉네임과 현재 프로필 사진은 공개합니다. 리뷰·저장 목록의 공개 범위와 차단·정지·탈퇴 조건은 별도로 적용합니다. [제품 정책](product-policy.md#프로필과-다른-사용자-접근) |

구버전 앱의 호환을 위해 기존 개인 숨김 기록과 API를 보존합니다. 새 앱의 조회와 개인화에는 이 기록을 적용하지 않습니다. [DEC-0042](decisions.md#dec-0042-개인-매장-숨기기-종료)

## 제보 사진과 프로필의 공개 범위

제보 사진은 본인과 등록 관리자만 열람합니다. 로그인과 소유권을 확인하며 제출된 증거는 관리자만 정리합니다. 소유자 불명 자료를 임의의 회원에게 연결하지 않습니다. 세부 허용·거절 조건은 [제보 사진 정책](product-policy.md#제보-사진)이 소유합니다.

비공개 프로필의 신원 정보 공개와 제보 증거 사진의 열람 제한은 서로 다른 정책입니다. 둘을 같은 이미지 공개 규칙으로 묶지 않습니다.

## 메뉴 원본과 직접 등록

메뉴 최신화에서 원본 부재 항목을 삭제하는 조건과 사용자 직접 등록 메뉴의 보호 예외는 [메뉴 등록 정책](../menu-registration-policy.md#5-섹션과-보강-정보)에서 관리합니다. 기존 DB에 있다는 사실과 사용자가 직접 등록했다는 근거를 구분합니다. 일반 관리자 확인이나 등록 범위 승인만으로 직접 등록을 추정하지 않습니다.

메뉴 수집의 전체 원문은 무손실 gzip 파일로 비공개 보관하며 신뢰된 수집·검증 작업만 읽습니다. 저장 위치를 옮길 때는 파일을 내려받아 복원한 원문이 기존 원문과 일치하는지 확인한 뒤 전환합니다. 스냅샷 식별자·수집 시점·추출 메뉴·기존 감사 기록은 보존하며, 저장 공간을 줄이려고 원문 증거를 생략하지 않습니다.

## 이미지 링크

### 저장과 전송

DB와 로그인은 Supabase에 유지하고 사진 파일의 이전 대상은 Cloudflare R2로 정합니다. 사진의 앱·서버 구현은 R2와 Supabase Storage를 사용합니다. 이전 저장소의 원본 파일과 위치 이력은 별도 정리 결정까지 보존합니다. 사진 제어 서버는 Supabase 세션과 기존 공개 범위·소유권·차단·관리자 권한을 확인한 뒤 전송을 허용합니다. 사진 저장소 변경만으로 새 로그인이나 별도의 사용자 계정을 만들지 않습니다. [DEC-0033](decisions.md#dec-0033-사진-저장소의-r2-이전)

| 사진 유형 | 전송 방식 |
| --- | --- |
| 공개 사진 | 별도 도메인 구매 없이 Cloudflare가 제공하는 Worker 주소를 사용합니다. Worker는 공개 사진용 저장소만 읽습니다. |
| 권한 확인이 필요한 사진 | 기존 Supabase 접근 정책을 통과한 요청에 짧은 수명의 서명 주소를 발급합니다. |

R2의 APAC 위치 힌트는 서울 리전 보장이 아닙니다. 단말 캐시와 서버의 파일 삭제 확인을 구분합니다. [DEC-0034](decisions.md#dec-0034-도메인-구매-없는-사진-주소)

### 이전과 삭제

이전 중에는 구버전 앱이 접근할 원본과 신규 사진의 호환 복사본을 유지합니다. 삭제와 계정 탈퇴는 모든 저장소의 복사본을 함께 정리하며, 물리 파일 정리에 실패하면 재시도 대상으로 남깁니다. 원본 보존 종료는 별도 운영 결정으로 다룹니다.

사진 저장소 이전은 현재 사용되는 사진과 보존이 필요한 증거를 대상으로 합니다. 종료된 이벤트에서만 쓰이거나 현재 참조가 없는 사진은 제외하되, 오늘 종료·미래 이벤트·현재 데이터에서 재사용하는 사진과 신고·제보 증거는 유지합니다. 제외는 원본 삭제를 뜻하지 않습니다. [DEC-0036](decisions.md#dec-0036-사용-중인-사진만-저장소-이전)

### 캐시와 링크 만료

임시 링크를 발급할 때 기존 열람 권한을 유지합니다. 캐시나 일괄 발급이 권한 검사를 우회하는 이유가 되어서는 안 됩니다. 계정이 바뀌거나 이미지가 교체되면 이전 결과의 재사용 범위도 확인합니다.

공개 사진에는 도메인 구매 없이 CDN 캐시를 적용합니다. 공개 파일 삭제는 원본과 CDN 캐시를 함께 정리하고 공개 주소에서 부재를 확인해야 완료됩니다. 캐시 정리에 실패하면 재시도 대상으로 남깁니다. 권한이 필요한 사진은 앱 디스크 캐시에 저장하지 않으며, 메모리 캐시도 현재 계정과 열람 범위의 접근 확인을 거쳐 재사용합니다. 서명 주소의 갱신만으로 같은 사진을 반복 다운로드하지 않되, 계정·접근 범위 변경으로 무효가 된 결과는 화면과 캐시에서 재사용하지 않습니다. 이미 내려받은 공개 사진의 원격 회수까지 보장하지는 않습니다. [DEC-0040](decisions.md#dec-0040-공개-cdn과-권한-사진-캐시의-분리)

리뷰·프로필 사진은 임시 링크 만료로 내려받지 못하면 기존 권한 확인 경로에서 새 링크를 받아 자동으로 다시 시도합니다. 접근이 거절되거나 새 링크로도 실패하면 재발급을 반복하지 않습니다.

프로필·리뷰 이미지 링크는 기본 일괄 발급을 채택했습니다. Redis를 쓰는 공유 캐시는 현재 선택의 전제가 아닙니다. [DEC-0003](decisions.md#dec-0003-프로필리뷰-이미지-url-기본-배치-발급-채택)

이미 발급된 서명 링크는 만료 전 소지자가 사용할 수 있습니다. 권한 변경과 링크 수명, 이미 내려받은 파일의 회수 가능성은 같은 보장이 아닙니다. 구체적인 만료 시간·배치 크기·동시성 수치는 구현에서 관리합니다.

## 요청 남용과 입력 오류

서버는 기능별로 요청을 제한하고 입력을 검증합니다. 한도에 걸리면 서버 장애와 구분해 처리하고, 앱에서는 필요한 재시도 안내를 제공합니다. [검색 정책](product-policy.md#지도와-검색)

| 기능 | 서버가 제한하는 범위 | 반복 요청 처리 |
| --- | --- | --- |
| 외부 장소 검색 | 클라이언트별·서비스 전체 검색 요청과 외부 제공자별 호출을 각각 제한합니다. | 서비스 전체 한도에 도달하면 클라이언트별 한도가 남아 있어도 검색을 제한합니다. |
| 리뷰 신규 작성 | 계정별 신규 작성 요청을 제한합니다. | 정해진 시간 안에 같은 내용으로 재시도하면 기존 리뷰를 반환합니다. |
| 피드백·매장정보 수정·미등록 매장 제보 | 유형별 서비스 전체 요청과 회원 계정별 또는 비회원 IP별 요청을 제한합니다. | 정해진 시간 안에 동일한 제보가 들어오면 중복 저장을 막습니다. |
| 미등록 매장 링크 검증 | 제보 접수와 별도로 계정 또는 IP 기준 한도와 서비스 전체 한도를 적용합니다. | 검증에 실패한 시도도 검증 요청으로 집계합니다. |
| 프로필 | 닉네임 중복 확인과 프로필 저장 요청을 각각 제한합니다. | 닉네임과 자기소개에는 실제 변경 횟수의 일일 한도도 각각 적용합니다. |
| 사진 업로드 | R2 신규 업로드 준비에 계정별 한도를 적용합니다. | 같은 업로드를 이어갈 때 기존 요청 기록을 사용합니다. |
| 푸시 등록 | 계정별 식별자 등록·변경 횟수와 등록 식별자 수를 제한합니다. | 등록 정보가 같은 요청은 변경 횟수에 포함하지 않고 갱신 시점만 제한합니다. |

분당·일일 한도와 중복 처리 시간은 운영 DB 설정과 서버 함수에서 확인합니다. 일일 한도는 한국 시각 자정을 기준으로 초기화합니다.

미등록 매장 링크는 서버가 단축 링크의 목적지와 지도 서비스의 실제 장소 정보를 확인한 뒤 접수합니다. 기존 앱의 저장 요청에도 같은 검증을 강제하며, 비회원과 일반 회원은 검증 결과를 직접 지정하거나 검증을 건너뛸 수 없습니다. 외부 서비스의 제한·장애로 확인하지 못한 링크는 유효하다고 간주하지 않으며, 매장이 없다는 결과와 일시적인 확인 실패를 구분합니다. 검증 요청에도 서버 측 한도를 적용합니다.

잘못된 자기소개 등 사용자 입력은 입력 오류로 처리합니다. 알림 webhook은 허용한 출처와 본문을 확인하고, 영업 상태 worker는 인증과 요청 형식·크기를 확인한 뒤 작업을 시작합니다. 거절된 입력으로 발송이나 수집을 시작하지 않습니다.

## 변경과 검증의 의미

Supabase의 스키마·권한·서버 함수·worker 코드는 Git에서 변경 이력을 관리합니다. Git에 파일이 있다는 사실은 운영 적용을 뜻하지 않습니다. DB 전체를 현재 migration 폴더만으로 재현할 수 있다고 가정하지 않습니다.

테스트 코드의 존재, HTTP 성공 응답, 실제 데이터 변경, 외부 provider 정상 동작, 기기 수신은 각각 다른 근거입니다. 현재 배포 상태와 작업별 결과는 PR·CI·배포 기록에서 확인합니다. 일반 운영 자료나 실제 사용자 정보는 위키에 옮기지 않습니다.
