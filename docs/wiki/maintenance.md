# LLM 위키 유지보수 정책

변경 담당자가 작업과 함께 위키를 갱신하고, 리뷰 담당자는 코드·근거·문서의 의미가 일치하는지 확인합니다. 세션 안의 작업 절차이며 예약 실행이나 대화 밖의 자동 수집을 뜻하지 않습니다.

## 기록 위치와 확정 기준

| 새로 알게 된 내용 | 소유하는 위치 | 기록 조건 |
| --- | --- | --- |
| 코드·테스트로 확인한 동작과 경로 | 관련 reference 페이지 | 근거 링크, 적용 범위, 확인 날짜와 기준 ref |
| 구현 규칙의 확정된 변경 | 해당 로컬 Ramap 스킬 | 스킬을 먼저 수정하고 위키에는 위치·영향만 연결 |
| 제품 정책의 확정된 변경 | [제품 정책](product-policy.md) 및 코드·테스트 | 사용자 확정 근거와 구현 상태 구분 |
| 위키 운영 절차 변경 | 이 문서 | 변경 이유를 결정 기록에 연결 |
| 확정 정책의 도입·변경·폐기 이유 | [결정 기록](decisions.md) | 분야 문서와 같은 변경에서 추가 |
| 근거가 부족한 재사용 지식 | [후보함](inbox/README.md) | 불확실한 범위와 확인 방법 |
| 일회성 로그·개인 대화·작업 보고 | 위키에 저장하지 않음 | 필요한 결론과 공개 가능한 근거만 요약 |

명시적인 사용자 요청과 기존 승인 범위로 확정할 수 있는 변경은 다시 승인받지 않습니다. 질문·제안·실험·다른 저장소의 관행은 확정 근거가 아닙니다. 코드에서 발견한 사실만으로 새 제품 정책을 확정하지 않습니다.

## 작업 시작과 종료

1. 관련 위키, 소유 스킬, 실제 코드와 테스트를 확인합니다. 문서의 경로가 오래되었으면 검색해 실제 위치를 찾습니다.
2. 작업 종료 전 기존 문서와 후보를 검색해 중복을 합칩니다. 바뀐 사실은 해당 문서에서 고칩니다. 매 작업마다 새 페이지나 결정 ID를 만들 필요는 없습니다.
3. 정책 의미가 확정되어 바뀌었다면 소유 문서와 결정 기록을 함께 수정합니다. 날짜, 이유, 근거, 반영 문서, 적용 상태, 대체한 ID를 남깁니다. 구현이 후속이면 완료로 적지 않습니다.
4. 관련 코드와 테스트를 다시 확인한 페이지에만 `last_verified`를 갱신합니다. 날짜는 Asia/Seoul 기준입니다. 링크 수정이나 검사 통과만으로 내용 전체를 재검증했다고 표시하지 않습니다.
5. `source_ref`에 확인한 커밋을 적습니다. 같은 작업의 미커밋 변경을 설명할 때는 기준 커밋에 `+ working-tree`를 붙이고 범위를 본문에 적습니다. PR에서 실제 변경과 대조하며, 병합 뒤 해당 영역을 다시 검증할 때 새 커밋으로 갱신합니다.
6. 아래 검사를 실행하고 PR의 위키 영향 항목에 변경 문서·정책 결정 ID 또는 영향이 없는 이유를 적습니다. 리뷰에서 의미를 확인한 뒤 일반 코드 리뷰 절차로 반영합니다.

```bash
python3 scripts/check_wiki.py
git diff --check
```

## 변경 종류별 점검

| 변경 | 함께 확인할 문서와 근거 |
| --- | --- |
| 기능·상태 전이·접근 조건 | 기능 지도, 제품 정책, 관련 ViewModel·domain 테스트 |
| 모듈·의존성·DI·플랫폼 | 모듈 구조, 아키텍처, 앱 실행 흐름, settings와 각 build 파일 |
| 공통 상태 관리·데이터 호출 | 설계 패턴 탐색, 소유 스킬, 공통 테스트 |
| 공통 UI·리소스 | 디자인시스템, 소유 스킬, 사용 화면 |
| API·스키마·등록·운영 동작 | 백엔드 문서, migration·함수·클라이언트, 배포 여부 |
| 빌드·테스트·CI | 검증 안내, workflow·convention plugin |
| 기능 삭제·경로 이동 | 연결된 위키 링크, 목차, 현행 설명 제거 또는 이동 |

불일치를 발견하면 구현 사실과 승인된 의도를 나눠 확인합니다. 명백한 경로 오류는 즉시 고치고, 규칙의 소유권이나 제품 의미가 불명확하면 후보로 남겨 근거를 보완합니다. 경과 날짜만으로 문서를 최신 또는 폐기 상태로 판단하지 않습니다. 관련 영역 작업과 릴리스 준비 때 다시 점검합니다.

## 후보와 결정의 수명

후보는 `candidate`에서 `promoted` 또는 `rejected`로 처리합니다. 실제 판단에 적용한 작업은 후보 본문에 근거와 함께 기록합니다. 여러 작업에서 반복되면 검토할 이유가 되지만 사용 횟수만으로 자동 승격하지 않습니다.

승격 시 소유 문서를 갱신하고 결정 기록을 추가한 뒤 후보의 대상 경로·결정 ID·사유를 채웁니다. 구현 규칙이면 로컬 스킬도 먼저 갱신하고 위키의 관련 참조 페이지를 대상 경로로 남깁니다. 기각 시 이유를 남깁니다. 이전 결정은 삭제하지 않고 새 결정의 `대체한 결정`으로 연결합니다. 현행 페이지에서는 폐기된 설명을 정리합니다.

## 공유 범위와 검사 한계

이 위키는 `docs/wiki/`만 새로 Git 추적 대상에 추가합니다. 기존 로컬 문서·운영 산출물·`AGENTS.md`·`.agents/`의 공유 범위는 바꾸지 않습니다. 로컬 전용 문서는 경로를 코드 표기로 안내하며 존재를 전제로 한 Markdown 링크를 만들지 않습니다. 토큰, 사용자 데이터, 비공개 URL, 원본 대화는 옮기지 않습니다.

`LLM Wiki` CI는 PR마다 메타데이터·로컬 링크·문서 앵커·결정 ID·후보 상태를 검사합니다. 검사기의 회귀 테스트도 실행합니다. 외부 URL 접속, 제품 의미, 배포 상태, 코드와 설명의 일치, 링크 대상의 Git 추적 여부 전체를 보증하지 않습니다. `git status --short --untracked-files=all`로 새 근거 파일이 포함되는지 확인하고, 로컬 전용 파일이 없는 checkout에서도 검사합니다. CI 필수 검사 지정은 GitHub 저장소 설정에서 별도로 관리합니다.
