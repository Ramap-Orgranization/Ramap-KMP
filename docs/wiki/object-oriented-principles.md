# Ramap 객체지향 원칙

구현·리뷰·테스트에서 준수해야 할 팀 객체지향 원칙입니다.

이 문서가 아래 원칙의 단일 원본입니다. 스킬과 에이전트 지침에서는 이 문서를 읽고 적용하며, 같은 규칙을 복제하지 않습니다. 위키 분리와 기존 기준 통합의 근거는 [DEC-0037](decisions.md#dec-0037-팀-객체지향-원칙의-위키-분리)과 [DEC-0038](decisions.md#dec-0038-기존-객체지향-개발리뷰-기준의-위키-통합)에 남깁니다. 구체적인 계층·모듈 배치, 구현 패턴과 서식 규칙의 소유자는 [개발 참고](engineering.md)에서 확인합니다.

## 원칙을 적용하는 기준

원칙은 책임 응집도, 변경 용이성, 잘못된 상태 방지를 판단하는 도구로 사용합니다. SOLID(SRP, OCP, LSP, ISP, DIP) 위반이 실제 변경 파급이나 잘못된 의존 방향을 만드는지 확인합니다.

객체지향 체조 원칙으로 깊은 중첩, 긴 메서드, 과도한 원시값, 책임 없는 데이터 객체를 찾되 기계적으로 강제하지 않습니다.

## 책임을 가진 객체에 행동을 둔다

- 도메인 규칙과 상태 변경은 책임을 가진 타입 또는 협력 객체에 둡니다.
- 객체의 상태를 꺼내 외부에서 판단하고 변경하기보다 의도를 객체에 명령하는 Tell, Don't Ask를 따릅니다.
- ViewModel은 UI 상태와 사용자 이벤트 조정에 집중합니다. 비즈니스 규칙은 ViewModel이나 Composable에 두지 않고 이를 책임지는 협력 객체에 둡니다. 구체적인 소유 계층은 아키텍처 지침을 따릅니다.
- Repository 인터페이스는 책임별로 나누고 서로 관계없는 기능을 하나의 계약에 추가하지 않습니다.

## 값과 컬렉션에 역할과 책임을 캡슐화한다

- 도메인 의미·단위나 유효성 검사 규칙이 있는 ID, URL, 날짜, 수량 등의 원시값은 적절한 `value class` 또는 도메인 객체로 감쌉니다.
- 컬렉션 자체에 비즈니스 동작이나 불변 조건이 있으면 일급 컬렉션으로 만듭니다. 검색·정렬·중복·최대 개수 등 해당 도메인의 동작과 규칙을 컬렉션 객체가 소유하게 합니다.
- 해당 값이나 컬렉션의 비즈니스 로직, 유효성 검사, 불변 조건은 책임을 가진 객체에 응집합니다. 호출부마다 같은 판단과 검증을 반복하지 않도록 합니다.

값과 그 값을 다루는 규칙을 함께 두어 역할과 책임을 드러내고, 잘못된 상태와 규칙의 분산을 줄입니다.

## 클래스의 생성과 의존성을 명시한다

- 비즈니스 규칙과 서비스에는 일반 클래스와 생성자 주입을 우선 사용하고, 객체 수명은 DI에서 관리합니다.
- `object`는 sealed 상태 값처럼 의도적으로 하나의 값만 필요한 경우에 사용합니다.
- 클래스를 `private`으로 선언하지 않습니다.

일반 클래스·생성자 주입과 `object`의 사용 범위는 [DEC-0011](decisions.md#dec-0011-비즈니스-규칙의-일반-클래스와-생성자-주입)의 승인된 기준을 유지합니다.

## 확장 함수는 책임이 명확한 예외에 사용한다

- 캡슐화보다 호출 편의만 제공하는 확장 함수는 지양합니다. 도메인 규칙이나 상태 변경을 확장 함수로 옮겨 책임을 분산하지 않습니다.
- 소유할 타입을 변경할 수 없고 책임이 명확한 외부 라이브러리 어댑팅이나 순수 표현 변환에만 확장 함수를 허용합니다.
- 예외를 사용하는 경우 handoff에 이유를 적습니다.

## 이름과 함수에서 의도와 책임을 드러낸다

- 함수 이름으로 동작, 결과, 역할과 부수 효과를 예측할 수 있어야 합니다.
- `get`, `set`, `process`, `handle`, `manager`, `util`처럼 책임을 숨기는 이름을 구체적인 도메인 동사로 바꿀 수 있는지 검토합니다. 함수 이름에서 `get`, `set` 접두사는 피합니다.
- 조회에는 `fetch`, `find`, `search`, 변경에는 `update`, `change`, `save`, Boolean 질의에는 `is`, `has`, `can`, `should`를 사용합니다.
- 이름이 현재 구현 세부사항을 불필요하게 노출해 교체 비용을 높이지 않도록 합니다. 호출자의 관심사가 단순 조회라면 `findById`보다 `find`처럼 의도 중심 API를 검토하되, 여러 조회 방식의 구분이 계약의 일부라면 모호한 이름을 강제하지 않습니다.
- 함수는 구별되는 책임, 추상화 수준 또는 변경 이유를 드러낼 때 추출합니다. 응집된 메서드를 줄 수만 맞추기 위해 나누지 않습니다.
- 상태 변경, 데이터 호출, 결과 처리는 각각 집중된 함수로 분리합니다.

## 지식의 중복과 추상화의 필요성을 판단한다

- DRY는 텍스트 중복보다 지식과 변경 이유의 중복을 기준으로 판단합니다.
- 인터페이스나 계층 추가는 실제 대체 가능성이나 책임 경계가 필요할 때 권장합니다.
- 단순 전달만 하는 UseCase나 Repository, 추측성 인터페이스처럼 의미 없는 계층을 만들지 않습니다.
- 불필요한 추상화나 의존성을 추가하지 않고 기존 패턴을 재사용합니다.
- UI 공통화는 코드 모양뿐 아니라 동일한 UI 역할, 상태와 변경 이유를 공유하는지 확인해 추출을 권장합니다. 공통화가 오히려 결합도나 조건 분기를 늘린다면 추출을 권장하지 않습니다.

## 주석보다 테스트로 역할과 책임을 드러낸다

객체의 역할과 책임, 정상 동작과 거절·경계 조건은 테스트 이름과 사례만으로 이해할 수 있도록 작성합니다. 테스트로 검증할 수 있는 규칙은 설명 주석보다 테스트로 표현합니다. 코드와 테스트로 드러나지 않는 결정 이유나 제약이 필요할 때만 짧은 주석을 남깁니다.

## 테스트를 위해 프로덕션 코드를 변경하지 않는다

테스트를 작성하거나 통과시키기 위한 목적만으로 프로덕션 코드를 변경하지 않습니다. 다음과 같은 변경을 금지합니다.

- 테스트에서 접근하기 위한 접근 제한자 변경. 예를 들어 `private`을 `internal`이나 `public`으로 완화하지 않습니다.
- 테스트 호출을 편하게 만들기 위한 기본 인자(default parameter) 추가·변경.

테스트 준비, 픽스처, 테스트 대역은 테스트 소스에서 구성하고 기존 프로덕션 계약을 통해 동작을 검증합니다. 테스트가 실제 제품 결함을 발견한 경우에는 요구 동작을 근거로 결함을 수정합니다.

외부에서 관찰 가능한 동작과 중요한 상태 전이를 테스트합니다. 테스트가 구현 세부사항에 결합되거나 mock 호출 횟수만 검증하지 않도록 합니다.

테스트 편의가 객체의 공개 범위와 호출 계약을 결정하지 않도록 캡슐화와 프로덕션 설계를 지킵니다.
