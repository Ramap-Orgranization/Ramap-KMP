# Ramap 메뉴 정리 및 등록 기준

최신 원본 스냅샷과 운영 DB의 메뉴를 대조할 때 적용하는 기준이다. 원본에 없는 사실은 추정하지 않으며, 자동 판정이 불확실하면 `수동 검토`로 남긴다.

## 1. 판정 상태

| 판정 | 의미 |
| --- | --- |
| 유지 | Ramap 등록 범위에 해당하고 현재 원본과 일치한다. |
| 추가 | 원본에는 있지만 DB에 없는 유효 메뉴다. |
| 삭제 | 등록 범위 밖이거나 확정된 중복·구형 메뉴다. |
| 업데이트 | 같은 메뉴의 가격·설명·사진·대표 정보가 변경됐다. |
| 수동 검토 | 메뉴 정체, 중복, 가격 충돌을 확정할 근거가 부족하다. |

## 2. 등록 범위

유지 대상은 라멘, 츠케멘, 마제소바, 아부라소바, 냉라멘, 라멘 본품이 명확히 포함된 세트, 토핑이 많아도 라멘 본품인 메뉴, 그리고 삿포로·하카타처럼 지명이 붙은 라멘이다. 이름만으로 불명확하면 설명까지 확인한다.

2026-10-08 사용자 재확인에 따라 **기존 DB에 등록된 메뉴는 무조건 라멘 등록 범위로 판정하며 범위 승인을 다시 요청하지 않는다.** 같은 매장에서 정규화 이름으로 기존 행과 대응되는 메뉴는 이름·설명·면 종류만으로 등록 범위를 다시 보류하지 않는다. 사용자의 명시적 제외 지시, 활성 `suppress`·제외 규칙, 확인된 판매 종료는 이 판정보다 우선한다. 신규 메뉴에는 이 규칙을 적용하지 않으며, 메뉴 정체·실제 구성 변화·다중 가격·숨김·이벤트는 라멘 범위와 구분해 필요한 값만 검증한다. 설명 문구만 달라진 경우는 아래 설명 갱신 규칙에 따라 처리한다. 정책 변경 시 이미 만들어진 통합 보류 목록 전체에도 적용하되, 사용자가 특정 선택 외의 보류를 유지하라고 지정한 배치에서는 그 보류와 DB 값을 보존한다.

**탄탄면·마제소바·츠케멘·중화소바 본품은 신규 메뉴를 포함해 자동 승인한다.** 중국식 탄탄면, 라구탄탄면(파스타), 괄호나 강조 표시가 붙은 본품도 이 범위 결정에 포함하며 일본식 여부를 다시 묻지 않는다. 이 자동 승인은 본품의 등록 범위이며 단독 면 추가·토핑·소스는 해당 본품으로 자동 등록하지 않는다. 숫자 가격, 실제 중복, 판매 상태 검증은 범위 승인과 구분한다.

메뉴명의 앞뒤 공백을 제거한 뒤 이름이 `라멘` 또는 `멘`으로 끝나면 라멘 메뉴로 판정한다. 예를 들어 `마라우육탕멘`은 이름이 `멘`으로 끝나므로 등록 범위에 포함한다. `나가사키짬뽕라멘`, `매운나가사키짬뽕라멘`처럼 짬뽕이 포함된 이름도 이 기준을 우선 적용하며, 설명이 없다는 이유로 범위를 수동 검토하지 않는다. 이 기준은 메뉴의 등록 범위에 대한 판정이며 가격 검증, 판매 상태, 활성 수동 오버라이드와 제외 규칙은 별도로 적용한다.

단독 토핑, 사이드, 음료·주류, 밥·덮밥, 카레, 일반 소바·우동·냉면·짬뽕, 초밥·마키, 디저트, 라멘 포함 여부가 불명확한 일반 세트, 공지성 행, 판매 종료·준비 중·품절 안내 행은 삭제 대상이다. 다만 이름과 설명만으로 정체를 확정할 수 없으면 삭제하지 않고 수동 검토한다.

**2026-10-08 사용자 확인: 신규 메뉴는 검증된 고정 가격이 8,000원 이하이면 가격만으로 사이드로 판정한다.** 이름이 라멘이거나 자동 승인 유형에 해당해도 이 신규 가격 기준을 먼저 적용한다. 기존 등록 메뉴, 사용자가 기존 메뉴 ID와 같은 메뉴로 확정한 항목, 사용자가 명시적으로 등록 승인한 항목과 활성 검증 upsert는 이 가격 기준으로 다시 제외하지 않는다. 숫자 가격이 없는 변동·범위 가격에서 금액을 추정해 이 기준을 적용하지 않는다. 이 기준만으로 기존 메뉴를 삭제하지 않는다.

## 3. 출처 우선순위와 수동 확인

### 미선택 보류의 재수집 제외

2026-10-08 사용자는 6차 체크 선택47건을 승인하며, 지금까지 미선택한 현재 보류37건(메뉴36건·원본 확인 실패 매장1곳)을 이후 수집에서 제외하도록 지시했다. 이 결정은 해당 동결 자료의 매장 ID·원본 ID·정규화 메뉴명에만 적용한다. 기존 등록 메뉴와 기존 보류는 보존하며 메뉴 삭제, 판매 종료, `suppress` 또는 등록 범위 재판정으로 확대하지 않는다.

재수집 제외는 해당 항목의 추가 원본 조회·사진 상세 수집·판정·자동 갱신·새 보류 및 승인 항목 생성을 건너뛴다는 뜻이다. 매장 전체 원문 DOM에 해당 행이 포함돼도 보존된 원문을 임의로 잘라내지 않는다. 기존 등록 메뉴의 라멘 판정을 다시 묻지 않는다. 원본 확인 실패 매장은 전체 자동 수집을 제외한다. 매장별 이름 또는 브랜드 공통 규칙으로 확대하지 않으며, 가격 변화만으로 제외를 해제하지 않는다. 사용자가 해당 항목의 재수집을 명시적으로 요청하면 정확한 제외 기록을 해제하고 DB 감사와 로컬 캐시를 함께 갱신한다.

DB `shop_menu_validation_runs.details`의 `collection_skip_authority=human_user`와 `collection_skip_bindings`에 결속해 보존하고, `tools/menu-refresh/data/collection-skips.json`을 검증된 DB 기록의 수집기 캐시로 사용한다. 최신 DB 상태의 제외 기록을 우선하며 `suppress`·삭제용 제외 규칙과 분리한다.

### 매장 정체와 명칭 변경

2026-10-08 사용자 지시에 따라 기존 DB와 현재 네이버 원본의 **Place ID와 주소가 모두 일치하면 같은 매장으로 판정하고 명칭 변경을 확정한다.** 네이버의 현재 매장명을 기존 행에 반영하며, 별도의 공식 개명 공지나 사용자 재승인을 요구하지 않는다. 주소 비교에서 공백·시도 약칭·층 등 상세 표기의 유무만 다른 경우는 같은 주소로 보되, 도로명·번지·건물번호가 다른 경우까지 동일 주소로 확대하지 않는다. 사용자가 특정 매장명이나 주소 수정 범위를 지정한 경우에는 그 지시를 우선한다.

유메식당(네이버 Place ID `1862315922`)과 네이버의 `Yumei`는 2026-10-08 사용자 확인으로 같은 매장이다. 주소는 `경기 안산시 상록구 학사2길 20`이며, 이름이 다르다는 이유로 지점 정체를 다시 보류하지 않는다. 이번 지시는 동일 매장 판정의 기록이므로 DB 매장명 `유메식당`을 유지한다. 이 확인은 매장 정체에 관한 것이며 메뉴 등록 범위를 확정하지 않는다.

메뉴별 출처 우선순위는 다음과 같다.

1. 활성화된 검증 수동 오버라이드
2. 명시적 근거가 있는 공식 출처
3. 네이버 스냅샷

수동 오버라이드는 매장 소유자·직원 확인, 공식 게시물 또는 관리자가 검증한 사실만으로 생성한다. 사용자의 명시적 변경 지시는 이 출처 우선순위보다 먼저 적용한다. 2026-10-07 상시 지시에 따라 같은 메뉴의 검증된 최신 단일 고정 가격과 사진은 기존 수동 확인 값과 달라도 승인 없이 갱신한다. 정규 메뉴와 활성 upsert의 해당 값을 같은 트랜잭션으로 동기화하고, 바뀐 확인 기록은 `admin_verified`와 최신 출처 근거로 기록해 과거 매장 확인 값인 것처럼 표시하지 않는다. 구성·판매 상태·등록 범위의 실제 충돌은 근거를 재검토하며, 가격이나 사진 값이 다르다는 사실만으로 작업을 보류하지 않는다.

활성 `suppress` 오버라이드는 같은 정규화 메뉴명의 스냅샷 재등록을 막는다. 활성 `upsert` 오버라이드는 스냅샷에 메뉴가 없어도 검증된 메뉴가 후보에 남도록 보호하며, 같은 메뉴의 스냅샷 값이 충돌해도 수동 확인 값만으로 가격 충돌 보류 대상이 되지 않는다. `review_after`는 알림·재검토용 날짜일 뿐이며, 날짜가 지나도 오버라이드나 정규 메뉴 데이터를 자동 변경하지 않는다.

관리자가 활성 `upsert` 기록으로 등록 범위를 확정한 메뉴는 같은 이름·설명 부재만을 이유로 범위를 다시 묻지 않는다. 갓라멘의 `갓소바(굵은면)`과 `갓소바(얇은면)`은 2026-10-06 사용자 승인으로 등록 대상이며, 매장별 활성 수동 확인 기록을 적용한다. 검증된 최신 가격·사진 변경은 즉시 동기화하고, 구성·판매 상태의 새 불확실성은 기존 범위 확인과 구분한다.

리틀훅라멘(네이버 Place ID `2023077622`)의 기존 DB 메뉴는 2026-10-07 사용자 지시에 따라 모두 라멘 등록 대상으로 확정한다. 확인 시점의 기존 메뉴는 `정구지로`, `온비빔` 2개이며 매장별 활성 `admin_verified` upsert로 이 결정을 보존한다. 이름이 라멘·멘으로 끝나지 않거나 설명이 부족하다는 이유로 두 메뉴의 등록 범위를 다시 보류하지 않는다. 이 개별 확인 기록은 두 메뉴에 적용하며 이후 새로 나타난 미등록 메뉴의 승인으로 확대하지 않는다. 다른 기존 등록 메뉴에는 2026-10-08의 공통 기존 메뉴 판정 규칙을 적용한다.

미노라멘 동명본점(네이버 Place ID `1100096792`)의 `상큼한 걸로`는 2026-10-07 사용자 승인으로 라멘 등록 대상이다. 확인 원본의 고정 가격은 11,000원이며 바질토마토 비빔면 설명·항목 사진과 원본 순서를 적용한다. 활성 `admin_verified` upsert로 범위 확인을 보존하고 같은 이름·설명만을 이유로 다시 보류하지 않는다. 이 확인은 해당 메뉴에만 적용하며 볶음밥 메뉴의 제외는 유지한다.

광화문라면 상암점의 `미소소바`(11,000원)와 고운라멘 반야월점의 `1인세트`(17,000원)는 2026-10-06 4차 테스트 미리보기의 사용자 승인으로 등록 범위가 확정됐다. 해당 매장의 활성 `admin_verified` 확인 기록을 적용하며 같은 범위를 다시 묻지 않는다. 다른 지점이나 일반 소바·세트 전체로 이 확인을 확대하지 않는다.

네코라멘의 `스파이시세트`(12,000원)와 단보라멘 순천향대점의 `면종류 1 + 사이드 메뉴 1`(11,000원)은 2026-10-06 5차 조사 후 사용자 승인으로 등록 범위가 확정됐다. 해당 매장의 활성 `admin_verified` 확인 기록을 적용하며 같은 이름·설명만을 이유로 다시 묻지 않는다. 다른 세트나 다른 지점으로 확인을 확대하지 않는다.

오버라이드의 `note`에는 개인 연락처, 실명 등 개인 정보나 DM·통화·대화 본문을 기록하지 않는다. 필요한 경우 확인 경로와 최소한의 운영 판단만 적는다.

### 네이버 메뉴 순서

네이버에 `추천 메뉴`와 일반 메뉴가 함께 있으면, 사용자에게 표시된 순서는 추천 메뉴를 먼저 두고 일반 메뉴를 뒤에 잇는다. 일반 메뉴에서 추천 메뉴와 정규화 이름·가격이 같은 항목은 중복으로 제거한다. 이후 등록 범위 필터를 적용한 남은 메뉴에 연속된 `display_order`를 부여한다.

## 4. 중복과 가격 충돌

동일 매장·동일 섹션 안에서 메뉴명은 앞뒤 공백 제거, 소문자 변환, 내부 모든 공백 제거로 정규화한다. 정규화 이름이 같으면 같은 메뉴이며 가격은 중복 식별값이 아니다. 같은 이름에 가격이 다르면 중복 신규 메뉴가 아니라 가격 충돌이다.

원본에서 정규화 이름·단일 고정 가격·설명 내용·카테고리와 구성이 같고 사진·대표 표시만 다르면 같은 메뉴의 중복 표현으로 처리한다. 원본의 대표 표시, 설명·사진 충실도, 첫 등장 순서로 대표 항목을 선택하고 DB는 메뉴 1개만 유지한다. 사진 선택을 사용자 승인 대상으로 남기지 않는다. 원본의 모든 행과 사진은 수집·스냅샷에 보존하고, 선택한 원본 ID와 동일 메뉴 판정 근거를 별도로 기록한다. 가격이나 구성이 실제로 다르면 이 병합을 적용하지 않는다.

의미상 중복 후보는 같은 매장에서 가격이 같고 설명 또는 사진이 같거나 매우 유사하며, 최신 원본에는 한쪽 이름만 있고 한쪽이 단순명·다른 한쪽이 매장 강조 또는 분류 표기일 때다. 최신 원본 표기를 우선하고 과거 단순명·구형 표기를 삭제한다. 최신 원본 존재, 강조·분류 표기, 설명·사진·대표 정보 충실도 순으로 살아남는 행을 결정한다. 어느 쪽도 확정할 수 없으면 수동 검토한다.

`(시오)/(쇼유)`, `(오리지널)/(카라이)`, `(연한맛)/(진한맛)`, `(고기추가)`, `(소)/(대)`, `(치즈×1)/(치즈×2)`, 포장 전용, 토핑·맵기·양·세트 구성 차이는 별도 메뉴일 수 있으므로 자동 중복 삭제하지 않는다.

동일 정규화 이름의 기존 DB 가격과 검증된 최신 원본의 단일 고정 가격이 다른 경우는 가격 변경이며, 사용자 상시 지시에 따라 기존 행을 즉시 업데이트한다. 같은 메뉴를 다른 가격의 신규 행으로 추가하지 않는다. 활성 upsert의 과거 가격도 같은 트랜잭션으로 갱신한다. 하나의 최신 원본 안에서 같은 메뉴가 여러 가격으로 나오거나 메뉴 정체·구성이 다른 경우에만 숫자를 임의로 선택하지 않는다.

## 5. 섹션과 보강 정보

정규 상시 섹션명은 `상시메뉴`이며, 상시 메뉴를 위해 새 섹션을 만들지 않는다. 한정·이벤트 섹션은 원본 근거가 있거나 검증 수동 오버라이드에 명시된 경우에만 사용한다. 섹션보다 최신 원본의 실제 메뉴명을 우선하고, 공백만 다른 같은 매장 섹션은 통합한다. 메뉴 삭제 뒤 비어 있는 구형 섹션은 함께 삭제한다.

기존 메뉴에는 중복 행을 만들지 않는다. 원본 사진·설명이 있고 DB에 없으면 각각 보강하며, 원본 `featured=true`이고 DB 대표가 아니면 대표 표시를 보강한다. 검증된 같은 메뉴의 원본 사진 변경은 사용자 상시 지시로 즉시 반영하며 활성 upsert에 과거 사진이 있으면 함께 갱신한다. 원본 사진·설명 부재만으로 기존 값을 지우지 않으며, 원본 `featured=false`만으로 기존 대표를 해제하지 않는다. 대표 정보의 실제 충돌은 별도로 검토한다.

**2026-10-08 사용자 지시: 큐멘의 동죽 쇼유 라멘처럼 같은 메뉴에서 원본 설명의 실제 내용 변경만 다른 경우는 사용자 검토 대상이 아니다.** 지점·메뉴 ID 대응과 원본 문자열을 확인한 뒤 설명을 원본 그대로 자동 갱신한다. 공백·줄바꿈뿐 아니라 실제 문구 변경도 포함한다. 활성 upsert가 해당 설명을 저장하고 있으면 정규 메뉴와 같은 트랜잭션으로 최신 설명을 동기화한다. 설명 차이만으로 메뉴 정체·구성 불명이라고 보류하지 않는다. 메뉴 ID 대응, 별도 항목의 다중 가격·구성, 판매 상태 등 설명 외의 실제 불확실성은 별도로 검사한다. 설명이 없는 원본으로 기존 설명을 자동 삭제하지 않는다.

DB에는 현재 원본에서 보이지 않는 기존 메뉴가 있을 수 있다. 이를 곧바로 오류나 삭제 대상으로 분류하지 말고 기존 등록 메뉴로 보존한다. 사용자가 직접 등록했다고 확인한 메뉴는 의도된 수동 등록으로 기록하고, 명시적인 삭제 근거가 없는 한 유지한다. 예를 들어 킨카라멘의 `머쉬룸시오라멘`은 사용자가 직접 등록한 메뉴다.

메뉴 행의 `source_url`은 사용자에게 보이는 원문 링크다. 사용자가 해당 메뉴의 원문 링크 저장을 명시적으로 요청한 경우에만 설정한다. 수집 출처와 감사 근거는 `shop_menu_snapshots.source_url`에 보존하며, 이를 `shop_menu_items.source_url`으로 복사하지 않는다.

## 6. 자동 처리 금지

변동·범위·시가 가격에서 원본에 없는 숫자를 만들지 않는다. 기존 DB가 이미 NULL 가격과 변동 표기로 등록돼 있으면 그 상태를 유지하면서 원본 가격 표기·순서·사진·설명을 갱신한다. 기존 고정 가격의 새 숫자를 확인할 수 없거나 신규 메뉴 가격 근거가 없으면 그 가격만 미확정으로 기록하고, 확인 가능한 기존 메뉴의 다른 필드를 함께 막지 않는다. 변동·범위 가격의 신규 등록을 사용자가 명시적으로 승인하면 숫자 가격은NULL로 두고 정확한 원본 `price_text`를 저장한다. 숫자 가격을 요구하는 upsert 제약은 바꾸지 않으며 해당 승인은 정확한 메뉴 ID·원본 ID·문구에 연결된 트랜잭션 감사로 보존한다. 추상적인 신규 메뉴명, 라멘 여부가 불명확한 일반 소바·세트, 구성 차이인지 불명확한 괄호, 실제 다중 가격·구성 충돌, 매장명만 같고 지점·주소가 확실하지 않은 경우는 근거를 추가 확인한다.

## 7. 안전한 적용 절차

### 사전 승인된 변경

사용자가 2026-10-07에 재확인한 상시 지시: **가격 변동, 메뉴 순서 갱신, 메뉴 추가, 삭제, 이미지 변경 작업은 사용자 승인을 받지 말고 바로 DB를 수정한다.** 이 다섯 종류의 변경은 매번 작업 승인이나 미리보기 승인을 요청하지 않는다. 필요한 원본 검증과 변경 계획을 내부에서 마치고 바로 반영한 뒤 결과를 보고한다.

2026-10-07 사용자 상시 지시에 따라 검증된 메뉴 가격 변경, 원본 순서 갱신, 메뉴 추가, 삭제 근거가 확인된 삭제, 같은 메뉴의 사진 변경은 승인 요청이나 승인 대기 없이 바로 DB에 반영한다. 2026-10-08에는 같은 메뉴의 설명 내용 변경도 자동 갱신하도록 추가 확인했다. 기존의 정확한 설명 동등성 결정은 유지하며, 나머지 검증된 설명 변경은 다시 승인받지 않는다. 메뉴 순서는 검증된 최신 원본의 추천 메뉴 우선·중복 제거 순서를 사용하고 설명은 원본 문자열을 그대로 저장한다.

이 지시는 승인 대기를 없애며 출처·매장·메뉴 정체와 등록 범위의 검증은 수행한다. 과거 DB·수동 기록과 최신 원본의 가격·사진이 다르다는 이유만으로 승인을 묻거나 보류하지 않는다. 검증된 단일 고정 가격이 바뀌면 `price_krw`와 이미 값이 있는 `price_text`, 활성 upsert의 과거 가격·사진을 함께 동기화한다. 원본에 숫자가 없거나 메뉴 정체·구성을 확정할 수 없는 경우에는 미확정인 값과 근거를 사후 보고하고 확인된 다른 변경은 진행한다.

추가는 등록 범위와 단일 고정 가격이 확인된 메뉴 또는 정확한 변동·범위 표기 등록을 명시적으로 승인한 메뉴에 적용한다. 삭제는 범위 밖·판매 종료·중복 등 삭제 사유가 근거로 확인된 메뉴에 적용한다. 최신 원본에서 안 보인다는 이유만으로 기존 메뉴를 삭제하지 않는다. 가격과 사진은 지점·메뉴 정체가 확인된 최신 원본 값을 사용한다. 메뉴명·별도 구성 변경, 대표 해제, 등록 범위나 실제 중복 관계의 불확실성은 별도로 확인하며 설명 문구만 다른 경우는 자동 갱신한다. 현재 미리보기를 명시적으로 승인한 경우에는 그 승인도 함께 적용한다. 사전 승인된 변경에도 변경 전 라이브 재검증, 삭제 ROLLBACK 검증, 사후 독립 정합성 검토를 적용한다.

1. 최신 원본 스냅샷과 운영 DB를 읽기 전용으로 대조하고, 수동 확인 근거와 오버라이드 필요 여부를 함께 검토한다.
2. 각 메뉴의 유지·추가·삭제·업데이트·미확정 값을 내부 계획에 기록한다. 검증된 최신 가격·사진과 과거 upsert의 차이는 자동 동기화 계획에 포함한다.
3. 사전 승인된 순서·같은 메뉴의 설명·추가·삭제·가격·사진 변경은 바로 진행한다. 사전 승인 범위 밖의 불확실성만 사용자에게 확인하며, 기존 대화에서 해당 미리보기를 승인했다면 같은 승인을 다시 요청하지 않는다.
4. 변경 직전에 매장 ID·이름·주소·메뉴 ID·가격과 활성 오버라이드 상태를 재검증한다.
5. 승인된 수동 확인이 있으면 오버라이드 생성·갱신과 정규 메뉴 변경을 같은 트랜잭션으로 적용한다. `suppress`는 재삽입 방지 목적만으로 섹션을 만들지 않는다.
6. 삭제 SQL은 먼저 `ROLLBACK`으로 검증한다.
7. 계획 수와 실제 처리 수가 같을 때만 `COMMIT`한다.
8. 삭제 대상 잔존, 유지 대상, 중복, 빈 섹션, 오버라이드 적용 결과를 사후 검증한다.
