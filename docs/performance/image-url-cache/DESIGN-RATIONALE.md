# 이미지 링크 캐시: 선택 근거와 남은 검증

> 후속 상태: 사용자 승인으로 기본 배치를 앱에 적용하고 Kotlin 코드로 재측정했다. 현행 적용 상태와 포트폴리오 수치는 [적용 후 보고서](APPLIED-BATCH.md)를 우선한다. 아래 내용은 해당 실험 시점의 기록이다.

2026-10-12 코드 및 공식 문서 대조. **구현 이후의 재평가**이며, 최초 구현 전에 모든 대안을 비교했다는 기록이 아니다.
기존 실측은 [RESULTS.md](RESULTS.md)에 보존한다. 이 문서의 제안을 승인된 제품 정책으로 취급하지 않는다.

후속 실험의 실제 수치와 채택 권고는 [동일 조건 비교](CONTROLLED-COMPARISON.md)에 기록한다.
아래 7절은 후속 실험을 설계할 당시의 검증 요구이며, 현재 검증 상태는 후속 보고서가 우선한다.

## 1. 먼저 해결 목표를 구분한다

- 한 목록에서 같은 작성자 사진을 여러 번 발급: 경로 중복 제거로 해결할 수 있다.
- 이미지별 클라이언트 왕복: 일괄 요청으로 줄일 수 있다.
- 다른 기기·서버 요청이 같은 유효 링크를 반복 발급: 공유 캐시가 해결하려는 문제다.
- DB Disk IO 경고: 어떤 쿼리/작업이 IO를 사용했는지 별도 확인이 필요하다.

현재 47.6%는 위 첫 세 변경의 결합 효과다. Redis 도입의 필요성이나 Redis 단독 효과는 입증하지 못했다.

## 2. 저장 대상과 실제 전략

이미지 원본은 Storage에 있다. Redis에는 재생성 가능한 `{url, expiresAt}`를 JSON 문자열로 저장한다.
단, signed URL은 소지자가 사용할 수 있는 접근 수단이므로 비밀 값처럼 다룬다. 앱에 Redis 자격 증명을 주지 않고
로그에도 URL을 쓰지 않는다. 권한 판정은 저장하거나 공유하지 않는다.

```text
앱에서 경로 중복 제거·묶음 요청
  → 요청자의 JWT로 Storage info 조회: 현재 권한 + 파일 버전 확인
  → 그 버전의 Redis 키 조회
     ├─ 만료 여유가 있는 값 존재 → 링크 반환
     └─ 없음 → 짧은 잠금 획득 → 캐시 다시 확인
                → Storage에서 새 링크 발급 → Redis 저장 → 반환
```

**Cache-Aside(필요할 때 애플리케이션이 채우는 캐시)**다. 여기서 애플리케이션은 Edge Function이다.
Redis가 Supabase를 자동 호출하지 않는다. 코드가 GET/발급/SET을 조율한다.
읽기 흐름 안에서 캐시에 쓰는 행위 자체를 도메인 데이터의 Write-Through라고 부르면 안 된다.
패턴 정의: [Microsoft Cache-Aside](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside).

| 전략 | 쉬운 설명 | 이 데이터에 대한 판단 |
| --- | --- | --- |
| Cache-Aside | 요청 때 캐시를 찾고 없으면 만들어 저장 | 어떤 사진을 볼지 미리 몰라도 되고, 만료 링크를 요청 시 재생성할 수 있어 적합한 후보. 첫 요청 비용 발생 |
| Read-Through | 캐시 계층이 원본을 가져오는 책임까지 맡음 | 별도 로더 계층을 만들 수 있지만 현재 Redis REST 자체에 Supabase 권한/발급 로더가 있지 않음. 지금 구현 명칭으로 쓰지 않음 |
| Write-Through | 원본 변경 시 캐시도 동기 갱신 | 사진 업로드 때 링크를 만들어도 보지 않는 동안 만료될 수 있음. 업로드가 없어도 링크 재발급이 필요해 이것만으로 해결되지 않음 |
| Write-Behind | 캐시에 먼저 쓰고 원본 반영은 나중에 함 | 임시 링크는 Redis에서 먼저 만들고 Storage로 나중에 반영하는 원본 데이터가 아님. 이미지 업로드의 비동기 저장 문제와 구분 |
| Refresh-Ahead | 만료 전에 미리 새 값을 준비 | 인기 사진의 첫 요청 지연을 낮출 후보. 보지 않는 사진의 불필요한 발급과 작업 실행·권한 관리 비용이 추가됨 |
| Stale-While-Revalidate | 이전 값을 먼저 주면서 뒤에서 갱신 | 아직 유효한 링크의 짧은 재사용 구간으로 설계할 수 있으나 만료 URL은 사용 불가. 현재는 백그라운드 갱신 없이 새 발급을 기다림 |

비교의 일반 개념: [Microsoft caching guidance](https://learn.microsoft.com/en-us/azure/architecture/best-practices/caching).

## 3. Redis를 선택할 수 있는 이유와 비용

- 여러 Edge 인스턴스·기기에서 같은 값을 공유할 외부 저장소가 필요하다는 요구에 맞는다.
- 인스턴스 메모리에만 두면 그 인스턴스 밖에서는 재사용이 안 된다. DB에 캐시를 두면 원래 우려한 DB에
  캐시 조회·쓰기 부하를 추가한다. Redis는 이 캐시 저장 부하를 별도 시스템으로 옮길 수 있다.
- Upstash REST는 코드의 `fetch`로 사용할 수 있어 직접 TCP 연결 풀을 관리하지 않는 구성이다.
  REST 왕복·외부 서비스 비용·장애 지점은 추가된다. TCP 방식과의 성능 우위는 측정하지 않았다.
  [Upstash REST API](https://upstash.com/docs/redis/features/restapi).
- JSON String 한 키에 URL과 만료 시각을 함께 둔다. 항상 두 값을 함께 읽고 교체하므로 필드별 갱신을
  위한 Hash나 순위/큐 구조가 필요하지 않다. **String이 Hash보다 빠르다는 비교 결과는 없다.**
- 원본 사진과 리뷰를 Redis에 영구 저장하지 않는다. 캐시 손실은 재발급 비용으로 복구할 수 있다.
  Redis 영속성·복제·메모리 설정을 직접 튜닝했다고 설명하면 안 된다.

핵심 가정은 **유효 기간 안에 다른 요청에서 다시 조회할 사진이 충분히 많다**는 것이다.
같은 자료를 반복한 벤치마크의 100% 적중률은 실제 서비스의 적중률을 입증하지 않는다.

## 4. 만료·변경·권한 처리

근거: [storage.ts](../../../tools/image-url-benchmark/archived-functions/image-signed-urls/storage.ts)의 상수,
`cacheKey`, `isValidSignedImage`; [handler.ts](../../../tools/image-url-benchmark/archived-functions/image-signed-urls/handler.ts)의 권한 조회 순서.

- 링크 수명 300초, 만료 60초 전부터 재사용 중단. Redis TTL은 `expiresAt - 현재 시각 - 60초`다.
  캐시를 읽어도 수명을 늘리지 않는 **절대 만료**다. URL의 실제 만료가 읽기 횟수로 늘어나지 않기 때문이다.
- 60초 여유는 수신 뒤 이미지 요청까지의 지연 등을 고려한 초기 설정이다. 실측 분포로 최적화한 값은 아니다.
  오래 열린 화면까지 보장하는 값도 아니다. 4분에 자동 갱신되는 것이 아니라 그 이후 요청 때 재발급한다.
- 5분은 기존 리뷰/커뮤니티 발급 기간과 맞췄다. **기존 내 프로필은 30분**이었다.
  공통 5분으로 바뀌면서 내 프로필 메모리 재사용 구간도 짧아진다. 자기 프로필만 반복 조회하는 경우의
  발급 빈도 증가 가능성을 별도로 평가해야 한다. 전체 사용 패턴에서 개선됐다는 근거는 없다.
- 키는 프로젝트·버킷·경로·object ID·버전·최종 수정 시각·수명을 해시한 값이다.
  다음 요청에서 새 버전을 확인하면 다른 키를 쓰고 이전 항목은 TTL로 정리한다. 해시는 암호화가 아니다.
- 캐시 반환 전에 현재 요청자의 Storage SELECT 권한을 재확인하므로 사용자별 권한을 캐시하지 않는다.
  권한을 통과한 사용자들은 같은 파일 버전의 링크를 공유할 수 있다. 이 전제는 info와 sign API에 적용되는
  정책이 호환된다는 조건을 포함한다. 정책이 API별로 달라지면 다시 검토해야 한다.
- 이미 받은 링크의 즉시 회수, 권한 확인 직후의 변경 경쟁까지 해결하는 설계는 아니다.

TTL과 **용량 초과 시 퇴출(eviction)**도 다르다. LRU는 오래 안 읽은 키, LFU는 덜 읽은 키를 우선 제거하는
정책이다. 현재 코드에는 LRU/LFU 선택이 없다. Upstash 공식 문서는 기본 퇴출 비활성화 및 활성화 시
`optimistic-volatile` 방식을 설명한다. 실제 Ramap 설정을 이번에 조회하지 않았으므로 기본값을 운영값으로
단정하지 않는다. 잠금 키도 퇴출되면 중복 억제 보장이 약해진다.
[Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/),
[Upstash eviction](https://upstash.com/docs/redis/features/eviction).

## 5. 동시에 요청하면 왜 잠금이 필요한가

빈 캐시에 10명이 동시에 GET하면 모두 미스로 판단해 10번 발급할 수 있다(cache stampede).
[redis.ts](../../../tools/image-url-benchmark/archived-functions/image-signed-urls/redis.ts)의 `SET lock owner NX EX 10`은
키가 없을 때만 10초짜리 발급 권한을 얻는다. 이긴 요청은 캐시를 다시 확인한 뒤 발급하고,
나머지는 150ms 간격으로 최대 약 5.5초의 대기 루프를 돈다. HTTP 왕복 때문에 실제 벽시계 상한은 더 길 수 있다.

- 재확인 이유: 다른 요청이 저장한 직후 우리가 잠금을 얻었을 수도 있다.
- Lua 저장/해제 이유: 현재 소유자 확인과 저장·해제를 한 Redis 연산으로 처리한다.
  이전 작업이 늦게 끝나 새 소유자의 잠금을 삭제하는 경쟁을 줄인다. Supabase 발급까지 한 트랜잭션은 아니다.
- 10초는 Storage 제한 3초와 Redis 제한 1초에 여유를 둔 초기값이다. 극단적인 지연/프로세스 정지에 대한
  보증이 아니며 잠금 갱신도 없다. 150ms 폴링은 동시에 기다리는 요청 수에 비례해 Redis 호출을 늘린다.
- Redis 장애, 잠금 만료/유실, 복제/장애 전환 상황에서는 중복 발급이 생길 수 있다.
  Upstash는 문서상 eventual consistency를 설명하며, 현재 REST 코드는 별도 일관성 토큰을 관리하지 않는다.
  **정확히 한 번 발급(exactly once) 보장이나 Redlock 구현이라고 설명하지 않는다.**
- 중복 발급은 주로 비용·성능 문제다. 접근 권한을 잠금 성공 여부로 허용하지 않는다.

근거: [Redis lock의 소유자 확인·만료](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/),
[Upstash consistency](https://upstash.com/docs/redis/features/consistency).

## 6. 장애 처리의 선택

현재는 Redis 실패 시 Storage 직접 발급으로 돌아간다. 링크 캐시 장애 때문에 사진이 전부 안 보이는 것을
줄이려는 가용성 선택이다. 권한 확인은 유지하지만 원본 서버 부하가 늘어난다는 비용이 있다.
해당 요청 안에서는 Redis 재시도를 중단하나, 여러 인스턴스에 걸친 circuit breaker나 전역 요청 제한은 없다.
정상 잠금 대기가 끝난 경우에는 추가 발급 대신 일시 오류를 반환한다.

DB 과부하 보호가 최우선인 경우에는 이 선택이 맞지 않을 수 있다. 제한된 우회 횟수·대기열·요청 제한·일시 오류
반환을 비교해야 한다. 이를 이미 구현한 보호 장치나 합의된 장애 정책으로 소개하지 않는다.

## 7. 후속 비교를 설계한 이유

현재 벤치마크는 앱의 개별 요청과 서버 배치 실행의 차이, 동시 실행 수 4→8, Redis 유무가 함께 달라졌다.
Redis의 순수한 효과를 보려면 **같은 Edge 실행 위치·입력·동시 실행 수·권한 조건에서 캐시 유무만 바꾼 비교**가 필요하다.
현재 운영 API에 공개 cache-bypass 파라미터를 추가하는 방식은 사용하지 않는다. 격리한 검증 환경에서 비교한다.

또한 Supabase는 [createSignedUrls](https://supabase.com/docs/reference/javascript/storage-from-createsignedurls)를 제공한다.
고유 경로를 버킷별로 묶으면 이번 입력은 프로필·리뷰 두 버킷이므로 원칙적으로 **일괄 발급 HTTP 요청 2개**로
구성할 수 있다. 후속 실험에서 HTTP API로 실제 2회 발급을 확인했으며, 실제 앱 SDK·UI 성능은 별도 검증 대상이다.
HTTP 요청 2개가 DB 쿼리 2개라는 뜻도 아니다.

비교해야 할 후보:

1. 중복 제거 + 버킷별 Supabase 일괄 발급. 외부 캐시 운영 비용 없는 단순 비교군.
2. 같은 Edge에서 중복 제거 + 일괄 발급, Redis 없음. 클라이언트 왕복/서버 위치 차이를 분리.
3. 같은 Edge에서 Redis 공유 캐시. 캐시가 비었을 때·적중할 때·실제 혼합 비율을 각각 측정.

원본 접근 횟수도 계산해야 한다. 중복 제거 후 고유 이미지 접근 N회, 캐시 미스 K회라면 현재 구조는
Storage info N회 + sign K회를 보낸다. 개별 직접 발급 N회와 비교해 Storage HTTP 횟수가 자동으로 감소하지 않는다.
서명 CPU 비용·권한 쿼리 비용·실제 디스크 접근은 서로 다르므로 별도 계측이 필요하다.

서버 캐시 유지 근거는 실제 재사용률, 전체/꼬리 지연, 신규 발급 수, 실패율, Redis 명령량·비용으로 판단한다.
TTL/여유 시간/동시성/잠금 수치는 이 결과에 따라 조정한다. 단순 일괄 발급과 차이가 작으면 Redis를 빼는 것도
검토할 수 있다. 목표와 허용 비용을 정하기 전에 임의의 개선율을 합격 기준으로 확정하지 않는다.

## 후속 비교 이전 설명의 한계

“기기 간 유효 링크 공유를 위해 Cache-Aside를 구현했고, 절대 만료·파일 버전 키·요청자별 권한 확인·
짧은 분산 잠금으로 재사용과 동시 미스를 다뤘다. 결합 벤치마크에서는 개선을 확인했지만 Redis 단독 효과와
필수성은 일괄 발급 비교군이 빠져 미확정이다. TTL과 장애 시 원본 우회도 운영 분포를 바탕으로 재평가할 항목이다.”
