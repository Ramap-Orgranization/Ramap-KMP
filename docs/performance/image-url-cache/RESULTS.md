# 프로필·리뷰 이미지 링크 캐시 전후 측정

> 후속 상태: 사용자 승인으로 기본 배치를 앱에 적용하고 Kotlin 코드로 재측정했다. 현행 적용 상태와 포트폴리오 수치는 [적용 후 보고서](APPLIED-BATCH.md)를 우선한다. 아래 내용은 해당 실험 시점의 기록이다.

> **이 문서는 기존 소규모 파일럿 기록이다.** [2026-10-12 기본 배치 포함 후속 비교](CONTROLLED-COMPARISON.md)에서
> 기본 배치의 중앙값은 207.54ms, Redis 전부 적중은 685.35ms였다. Redis 채택 판단과 포트폴리오 설명은
> 후속 결과를 우선한다. 아래 47.6%는 Redis 단독 효과를 입증하지 않는다.

## 확인한 결과

**공개 리뷰 20개에 필요한 링크를 받는 시간의 중앙값이 1,432.42ms에서 750.09ms로 47.6% 감소했다.**
캐시 적중 상태에서는 페이지당 신규 링크 발급이 41건에서 0건으로 감소했다.
이는 아래 조건에서 실행한 **소규모 HTTP 벤치마크**의 결과다. 앱 화면 표시 시간이나 운영 Disk IO의 개선율은 아니다.

2026-10-12 재평가: 같은 Edge에서 캐시 유무만 바꾼 비교와 Supabase 기본 `createSignedUrls` 비교가
빠져 있다. **Redis 채택의 필요성이나 최적성을 검증한 결과로 사용하지 않는다.**
전략별 선택 근거·비용·미검증 항목은 [설계 검토](DESIGN-RATIONALE.md)에 정리했다.

| 지표 | 기존 요청 흐름 재현 | 한 페이지 중복 제거만 적용 | 서버 배치 + Redis 적중 |
| --- | ---: | ---: | ---: |
| 측정 횟수 | 6 | 6 | 6 |
| 링크 준비 시간 중앙값 | 1,432.42ms | 1,193.66ms | 750.09ms |
| 최소–최대 | 1,238.00–1,917.47ms | 1,038.28–1,483.29ms | 442.89–1,121.67ms |
| p95, nearest rank | 1,917.47ms | 1,483.29ms | 1,121.67ms |
| 페이지당 클라이언트 HTTP 요청 | 41 | 22 | 1 |
| 페이지당 Storage 신규 발급 | 41 | 22 | 0 |
| 페이지당 Storage 권한/정보 조회 | 0 | 0 | 22 |
| 페이지당 Redis REST 호출 | 0 | 0 | 22 |
| 측정 중 실패 | 0 | 0 | 0 |

6개 표본의 p95는 최댓값과 같다. 꼬리 지연이 안정적으로 개선됐다는 주장에는 쓰지 않는다.
중앙값 개선율은 `(1432.42 - 750.09) / 1432.42 × 100 = 47.6348%`다.
클라이언트 HTTP 요청은 `(41 - 1) / 41 × 100 = 97.6%` 감소했다.

## 첫 요청의 비용

캐시가 비어 있던 첫 요청도 제외하지 않고 원본의 `preparation`에 보관했다.

| 항목 | 최초 요청 실측 |
| --- | ---: |
| 전체 이미지 | 22개 |
| 기존 캐시 재사용 | 0건 |
| 신규 링크 발급 | 22건 |
| 링크 준비 시간 | 2,214.51ms |
| 함수 내부 처리 시간 | 830.11ms |
| Storage 권한/정보 조회 | 22건 |
| Redis REST 호출 | 88건 |
| 실패 / 캐시 우회 | 0건 / 0건 |

처음 캐시를 채울 때는 조회·잠금·발급·저장 작업이 필요했다. 이후 6회 조회에서 132개 링크를
재사용했고 신규 발급은 0건이었다. **처음부터 항상 빨라진다고 말할 수는 없다.**
최초 표본은 1회뿐이며, 빈 캐시 비용과 최초 함수 실행·네트워크 준비 비용을 따로 분리하지 않았다.
전체 클라이언트 시간과 함수 내부 시간의 차이를 전부 Redis 비용이나 서버 시작 비용으로 간주하지 않는다.

## 무엇의 효과인가

1. **목록 안의 중복 제거:** 작성자 프로필 사진 20개가 같은 경로였다. 한 번만 요청하면서
   발급 수가 41건에서 22건으로 감소했다. 중복 제거만 한 비교군의 중앙값은 16.7% 짧았다.
2. **Redis 재사용:** 프로필 1개와 리뷰 사진 21개의 이미 발급된 링크를 서버에서 재사용했다.
   따뜻한 캐시 표본의 `cacheHits = 22`, `issued = 0`, `cacheBypasses = 0`을 모두 확인했다.
3. **서버 배치 처리:** 앱에서 이미지마다 요청하던 흐름을 한 번의 함수 요청으로 묶고,
   함수 안에서 최대 8개씩 처리했다. 기존 리뷰 사진 요청의 동시 실행 수는 4개였다.
   Redis 방식과 중복 제거 비교군 사이의 37.2% 시간 차이는 **이 구조 변경까지 포함한 값**이다.

캐시 적중에도 기존 RLS를 통과하기 위한 Storage info 요청은 이미지마다 남아 있다.
기존 방식 대비 따뜻한 캐시의 Storage HTTP 요청은 페이지당 41건에서 22건으로 줄었지만,
중복 제거 비교군과 Redis 비교군의 Storage HTTP 요청 수는 모두 22건이다.
**Redis만으로 DB 조회나 Disk IO가 추가로 얼마나 줄었는지는 이번 측정에서 확인하지 않았다.**
최초 요청의 Storage HTTP 요청은 44건으로 기존 41건보다 많았다.
Redis REST 호출 수는 Lua 내부 명령 수나 Upstash 청구 단위와 동일하지 않다.

## 재현 조건과 원본

- 측정 시각: **2026-10-11 08:18:49–08:20:25 KST**
  (`2026-10-10T23:18:49.380Z`–`23:20:25.793Z`).
- 환경: 로컬 macOS arm64, Node v24.18.0. 함수 실행 리전 `ap-southeast-2`.
- 대상: 운영 ramap의 anon 권한으로 조회 가능한 동일 공개 프로필의 첫 리뷰 페이지.
  리뷰 20개, 작성자 사진 등장 20회(고유 1개), 리뷰 사진 21개(고유 21개).
- 세 방식은 같은 입력 파일·권한·유효 기간 300초를 사용했다. 표본 사이 4초 간격,
  6가지 실행 순서 순환, 오류 재시도 0회. 이미지 바이트는 내려받지 않았다.
- 비교 전 Storage info GET 2회를 별도 기록했다. 측정용 DB 쓰기·RLS 변경·Redis 초기화는 하지 않았다.
- Storage HTTP 요청: 준비 2건 + 최초 함수 44건 + 기존 246건 + 중복 제거 132건 + Redis 적중 132건 = **556건**.
  여기에는 입력 자료 수집용 공개 리뷰 RPC와 이전의 2개 이미지 연결 확인 요청은 포함하지 않는다.
- 기준 코드: `33a0d49c2731e42144f2c79704748d7c7e0cf68b`.
  `RemoteReviewDataSource.signReviews`와 `ReviewImageSigner`의 호출 순서를 Node로 재현했다.
  Android/iOS 앱 바이너리나 실제 UI에서 직접 측정한 값은 아니다.
- 배포 함수: `image-signed-urls` **v2 ACTIVE**, `verify_jwt=true`.
  배포 응답의 bundle SHA-256: `585518cb77b64d519a0766c1639d45dc37f1c7c3b3eaaae6591f735a2ef73075`.
- 서버 소스·측정 스크립트·입력 자료의 SHA-256은 [원본 결과](pilot.json)의 `source`에 보관했다.
  입력 경로와 사용자 ID는 공개 결과에서 제외했다.
- [측정 도구와 실행 방법](../../../tools/image-url-benchmark/README.md).

`pilot.json`은 전체 18개 측정 표본, 첫 요청, 준비 요청, 실패 수를 담는다.
기존/중복 제거 방식의 발급 수는 측정 클라이언트가 센 실제 HTTP 요청 수다.
Redis 방식은 서버가 실제 Storage/Redis 호출 위치에서 센 수치를 `X-Image-Metrics`로 받아 저장했다.
같은 JSON이 함수 로그에도 기록된다. 이번에는 Supabase 로그 조회 도구의 스키마/백엔드 오류로
독립 로그 집계까지 대조하지 못했다. 로그 대조가 완료됐다고 주장하지 않는다.

## 이력서/포트폴리오 표현

지금 근거로 사용할 수 있는 예시:

> Supabase 이미지 링크 발급을 Edge Function·Redis 캐시와 요청 일괄 처리로 개선.
> 리뷰 20개를 재현한 HTTP 벤치마크에서 캐시 적중 시 링크 준비 시간 중앙값을
> 1.43초에서 0.75초로 47.6% 단축하고, 페이지당 클라이언트 요청을 41회에서 1회로 감소시킴
> (방식별 6회 측정, 최초 캐시 생성 시간 별도 기록, 요청자별 접근 권한 검사 유지).

포트폴리오 본문에는 최초 요청 2.21초, 표본 수, 전체 측정값, 비교 코드, 장애/권한 테스트를 함께 제시한다.
현재 수치로 “앱 화면 47.6% 빨라짐”, “운영 Disk IO 47.6% 절감”, “Redis만으로 47.6% 개선”,
“모든 이미지 요청 100% 제거”라고 쓰면 측정 범위를 넘어선다.

앱 배포 후에는 동일 화면·기기·네트워크에서 UI 측정 표본을 늘리고, 동일 길이의 운영 기간별로
화면 조회 수/이미지 수당 발급 수·캐시 적중률·실패율·지연을 비교한다. Disk IO는 별도 DB 지표와
다른 쿼리 작업량을 함께 확보해 분석한다. 현재 배포 앱에는 이 변경이 아직 포함되어 있지 않다.
