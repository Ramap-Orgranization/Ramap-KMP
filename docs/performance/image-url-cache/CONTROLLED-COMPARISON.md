# 기본 배치 · Edge 배치 · Redis 실제 비교

> 후속 상태: 사용자 승인으로 기본 배치를 앱에 적용하고 Kotlin 코드로 재측정했다. 현행 적용 상태와 포트폴리오 수치는 [적용 후 보고서](APPLIED-BATCH.md)를 우선한다. 아래 내용은 해당 실험 시점의 기록이다.

2026-10-12 KST. **현재 코드와 이번 입력에서는 Redis 채택을 권하지 않는다.**
우선 후보는 중복 경로를 제거한 Supabase 기본 일괄 발급이다. 서버에서 입력 검증·관측·요청 제한을
중앙 관리할 별도 요구가 있다면 Redis 없는 Edge 배치를 선택할 수 있다.
이는 실험에 따른 권고이며, 운영 아키텍처 전환을 승인받거나 앱에 반영한 기록은 아니다.

## 1. 무엇을 실제로 비교했나

같은 공개 리뷰 20개, 이미지 등장 41회, 고유 이미지 22개(프로필 1 + 리뷰 21)를 사용했다.
중복 제거 이후의 같은 22개 링크를 모두 받는 HTTP 시간을 비교했다. 모든 방식은 같은 anon JWT의
현재 RLS 권한, 300초 링크 수명, 같은 로컬 macOS arm64 / Node v24.18.0 클라이언트를 사용했다.

- 주 비교 3방식 각 30회. 순서 6가지를 순환하고 표본 사이 2초, 페이지 동시 실행 1개.
- Edge는 모두 동일한 임시 함수, 시드니 `ap-southeast-2` 실행. 응답 헤더에서 리전을 매번 확인했다.
- 직접 배치와 Edge 배치는 **동일한** [batch-sign.mjs](../../../tools/image-url-benchmark/batch-sign.mjs)를 사용했다.
- Redis는 현재 운영 소스의 4모듈을 복제하고 **캐시 키 namespace만 격리**했다. 권한 확인, 잠금,
  재확인, 만료, 발급, 장애 우회 로직과 동시 이미지 처리 상한 8은 유지했다.
- 기본 배치는 버킷당 1요청이라 동시에 2요청을 보낸다. 하위 요청 수·알고리즘까지 같다고 가정하지 않는다.
  서버 위치와 캐시만의 효과는 추가 대조군으로 분리했다.
- 이미지 바이트 다운로드, UI 렌더링, 실기기 SDK, 운영 동시 접속 부하는 측정하지 않았다.

Supabase 기본 `createSignedUrls`는 여러 경로를 한 번에 처리하며 `storage.objects`의 SELECT 권한을
요구한다. 권한을 생략하거나 service-role로 바꾼 비교가 아니다.
[공식 API 문서](https://supabase.com/docs/reference/javascript/storage-from-createsignedurls),
[리전 지정 문서](https://supabase.com/docs/guides/functions/regional-invocation).

## 2. 결과

단위는 ms, 낮을수록 좋다. p50은 중앙값, p95는 표본의 95% 지점이다.

| 방식 | n | p50 | p95 | 평균 | 실패 페이지 |
| --- | ---: | ---: | ---: | ---: | ---: |
| ① 기본 배치 직접 호출 | 30 | **207.54** | **501.04** | 270.89 | 0 |
| ② Edge + 기본 배치, Redis 없음 | 30 | 317.62 | 579.12 | 396.23 | 0 |
| ③ Redis, 전부 적중 | 30 | 685.35 | 926.79 | 645.17 | 0 |
| ③ Redis, 전부 빈 캐시 | 6 | 860.36 | 1,043.22 | 840.70 | 0 |
| ③ Redis, 이미지 절반 적중 | 6 | 658.96 | 801.54 | 668.67 | 0 |
| 보조: 현재 개별 처리 + Redis만 끔 | 10 | 628.24 | 857.40 | 669.02 | 0 |

Redis에 가장 유리한 **100% 적중 조건**에서도 ①의 p50은 ③보다 **69.7% 짧았고**, ②는 **53.7% 짧았다**.
이 비율은 이번 비교군 간 중앙값 차이다. 실제 앱 전후 개선율, 기존 파일럿 대비 변화율로 사용하지 않는다.

빈 캐시·혼합 캐시는 각 6회뿐이다. 혼합 캐시 중앙값이 전부 적중보다 조금 낮게 나온 것은 서로 다른
표본 시점·네트워크 변동을 포함한다. 이 결과로 “미스가 있으면 더 빠르다”거나 적중률별 성능 곡선을 주장하지 않는다.

### 같은 라운드끼리 비교

| 비교 | 앞 방식이 빠른 횟수 | 뒤 방식 − 앞 방식 평균 | 평균 차이 bootstrap 95% 구간 |
| --- | ---: | ---: | ---: |
| ① 대 ② | 25 / 30 | +125.34ms | +57.92 ~ +192.87ms |
| ① 대 ③ 적중 | 28 / 30 | +374.28ms | +304.13 ~ +445.26ms |
| ② 대 ③ 적중 | 25 / 30 | +248.94ms | +165.99 ~ +332.51ms |
| ③ 적중 대 동일 코드 Redis 없음 | 7 / 10 | +28.84ms | **−65.78 ~ +120.47ms** |

마지막 줄은 캐시를 제외한 처리 순서와 동시성까지 같은 대조군이다. 이 10쌍에서 Redis의 평균 이득은
28.84ms였고 구간은 0을 포함했다. **Redis만의 일관된 지연 개선은 이번 표본으로 입증하지 못했다.**
표본 수가 다른 전체 중앙값 685.35와 628.24만 빼서 캐시의 인과 효과라고 해석하지 않는다.

bootstrap은 고정 seed, 10,000회로 라운드 쌍을 재표집했다. 한 시점의 순차 실험이므로 독립적인
여러 날짜·사용자·부하를 대체하지 못한다. p95도 운영 SLO의 보증 수치가 아니다.

## 3. 링크 발급을 없앴는데 왜 느린가

페이지당 실제 계측값이다. **HTTP 요청 횟수와 링크 개수를 구분**한다.

| 방식 | 클라이언트 HTTP | Storage info | Storage sign HTTP | 새 링크 | Redis REST |
| --- | ---: | ---: | ---: | ---: | ---: |
| ① 기본 배치 | 2 | 0 | 2 | 22 | 0 |
| ② Edge 배치 | 1 | 0 | 2 | 22 | 0 |
| ③ 전부 적중 | 1 | 22 | 0 | 0 | 22 |
| ③ 전부 미스 | 1 | 22 | 22 | 22 | 88 |
| ③ 절반 적중 | 1 | 22 | 11 | 11 | 55 |
| 보조 Redis 없음 | 1 | 22 | 22 | 22 | 0 |

현재 캐시는 [handler.ts](../../../tools/image-url-benchmark/archived-functions/image-signed-urls/handler.ts)의 이미지 처리에서
`authorize()`를 먼저 실행한다. 캐시에 링크가 있어도 **현재 사용자가 볼 수 있는지, 파일 버전이 무엇인지**
Storage에 이미지마다 확인한 뒤 Redis를 조회한다. 권한을 캐시하지 않으려는 선택의 비용이다.

```text
기본 배치: 22개 경로 → 버킷 2개로 묶어 Storage 발급 2요청 → 22개 링크
Redis 적중: 22개 경로 → Storage 정보 22요청 → Redis GET 22요청 → 기존 링크
```

배치 방식의 Storage HTTP는 2회이고 Redis 적중은 22회다. 기본 배치로 바꾸는 경우
Storage HTTP 요청 수는 이 조건에서 **90.9% 감소**한다. 이것이 DB 쿼리나 Disk IO 90.9% 감소라는 뜻은 아니다.

**Disk IO는 측정하지 않았다.** 서명 연산을 없앤 효과, RLS 쿼리 비용, 버퍼 적중, 실제 디스크 읽기·쓰기를
분리하지 못했다. 따라서 원래 경고 메일의 원인이나 DB 비용 절감을 이번 실험으로 확정하지 않는다.

## 4. 비용과 운영 복잡성

가격은 2026-10-12 공식 공개 가격 기준이다. 실제 계정 청구서나 현재 계약 조건의 검증은 아니다.
Upstash PAYG는 10만 명령당 $0.20, Free는 월 50만 명령이다. PAYG에는 Free의 50만 명령을
공제하지 않는다. [Upstash 요금](https://upstash.com/pricing/redis).

다음은 **22개 이미지가 100% 적중하는 이상적 조건에서 GET만 계산한 값**이다.

| 월 페이지 요청 | Redis GET | PAYG 명령 비용만 | Free 명령 한도 내 여부 |
| --- | ---: | ---: | --- |
| 1만 | 22만 | $0.44 | 이 사용만 있다면 가능 |
| 10만 | 220만 | $4.40 | 초과 |
| 100만 | 2,200만 | $44.00 | 초과 |

1페이지당 22 GET이면 다른 사용이 전혀 없어도 약 **22,727페이지/월**에서 Free 명령 예산에 도달한다.
초기 적재·미스·잠금 대기·다른 기능의 Redis 사용은 추가다. 실제 서비스 요청량과 적중률은 수집하지 않아
Ramap의 실제 월 비용으로 제시하지 않는다. 저장공간·대역폭·세금·추가 리전도 위 표에 포함하지 않았다.
미스 시 EVAL/Lua 내부 명령의 청구 집계는 이번에 검증하지 못했으므로 **88 REST 호출 = 88 청구 명령**으로 계산하지 않는다.

②와 ③은 페이지당 Edge invocation 1회도 사용한다. Supabase의 Free 포함량은 50만, Pro는 200만이며
유료 초과분은 **100만 단위로 올림하여 $2**다. Free 초과를 자동 유료 종량제로 가정하지 않는다.
①은 이 기능을 위한 별도 Edge 호출이 없다.
[Supabase Edge 과금](https://supabase.com/docs/guides/platform/manage-your-usage/edge-function-invocations).

| 부담 | ① 기본 배치 | ② Edge 배치 | ③ 현재 Redis |
| --- | --- | --- | --- |
| 별도 배포 서버 코드 | 없음 | 함수 1개 | 함수 + Redis 연동 |
| 권한 처리 | 기존 Storage RLS | 호출자 JWT로 기존 RLS | 매 이미지 info + 발급 RLS |
| 캐시 만료·파일 변경 | 별도 공유 캐시 없음 | 별도 공유 캐시 없음 | TTL·만료 여유·버전 키 |
| 동시 미스 제어 | 필요 없음 | 필요 없음 | 임시 잠금·소유자 확인·대기·유실 처리 |
| 추가 장애 지점 | 없음 | Edge | Edge + Redis |
| 운영 항목 | 배치 부분 오류 | 배포·로그·리전 | 왼쪽 + 토큰·한도·적중률·잠금·장애 우회 |

여기서 “별도 없음”은 이 기능에 추가되는 구성요소를 말한다. Storage 자체의 비용/장애가 없다는 뜻은 아니다.
월 몇 달러라는 비용만으로 Redis를 배제하는 판단은 아니다. **이번에는 더 빠른 단순 대안이 있고,
추가 운영 책임을 상쇄할 성능·DB 비용 이득이 확인되지 않았다.**

## 5. 권고와 다시 검토할 조건

1. **우선 ①을 앱 적용 후보로 선택한다.** 인앱 영속 캐시를 추가하는 방식이 아니다. 요청 안에서 경로를
   한 번만 보내고 Supabase가 제공하는 기본 일괄 발급을 사용한다. Kotlin SDK의 부분 오류 처리·세션 변경·
   취소 동작을 유지하는 통합과 실기기 검증은 후속 작업이다.
2. **서버에서 관리해야 할 구체적 요구가 있으면 ②를 선택한다.** 같은 측정에서 ③보다 p50이 53.7% 짧고
   Redis·잠금·TTL 운영이 필요 없다. 이번 임시 함수가 운영용 요청 제한까지 구현한 것은 아니다.
3. **③을 유지할 근거는 현재 부족하다.** 실제 TTL 안의 재사용률, 서명 자체의 DB/CPU 비용,
   다중 인스턴스 동시 미스 부하를 계측해 단순 배치 대비 이득이 나올 때 다시 검토한다.
   성능을 위해 권한 검증을 임의로 생략하지 않는다. 권한 조회의 안전한 배치화 등 다른 구조는 별도 실험 대상이다.

확실도: **이 22개 이미지 워크로드에서 ①·②가 현재 ③보다 빠르다는 판단은 높음**.
다른 화면·네트워크·회원별 비공개 권한·대규모 동시성·운영 Disk IO에 대한 일반화는 미검증이다.
프로필 단독 조회와 기존 내 프로필 30분 → 5분 링크 수명 변경의 영향도 포함하지 않았다.

## 6. 재현·실패 기록·로그 대조

- 본 실행: **2026-10-12 10:20:07–10:25:19 KST**, 112개 측정 페이지 + 12개 준비 페이지.
  본 실행의 이미지 오류 0, 캐시 상태 불일치 0. Storage 1,928 HTTP, Redis 1,848 REST 호출.
- 준비의 토큰 거절 확인을 포함한 Edge 호출 94회. 계측 로그가 있는 정상 처리 요청은 93회다.
- **서버 로그 대조 성공:** 해당 시간 구간의 request ID로 Supabase `function_logs.event_message`를
  집계해 93개 요청, 신규 링크 1,188개, 캐시 적중 792개가 응답 헤더 합계와 일치했다.
  직접 발급 31페이지의 682개 링크는 Edge 로그에 없으며 클라이언트 계측이다.
  로그와 헤더는 같은 계측 코드에서 나온다. Storage 내부 쿼리 로그나 Redis 청구서의 독립 검증은 아니다.
- 준비 실행 2건은 실패하여 중단했고 원본을 보존했다. 첫 실행은 Edge 자동 서울 배치였고,
  두 번째는 시드니에서 cold 캐시의 Storage info 1건이 실패했다. 각각 이미지 오류 1개다.
  이후 리전 강제 검증과 연속 3실패 중단 규칙을 적용했다. 본 표본을 재시도해 성공으로 대체하지 않았다.
- 전체 이번 작업의 Storage HTTP 호출 시도는 API 응답 형태 확인 2 + 중단 실행 47 + 91 + 본 실행 1,928 = **2,068회**.
  실제 운영 트래픽은 별도로 존재할 수 있다. 이를 프로젝트 전체 요청 수라고 표현하지 않는다.
- 준비 오류는 권한/파일 정보 요청의 실패까지 계측됐다. 타임아웃인지 다른 일시 오류인지 세부 원인은
  이번 비식별 계측만으로 확정하지 않는다. 서명·Redis 오류로 단정하지 않는다.
- p50/p95 선형 보간, 짝지은 차이 및 bootstrap 계산은 재현 스크립트에 있다.
  기존 파일럿은 다른 시각·동시성·nearest-rank를 사용했으므로 새 전후 비교군으로 섞지 않는다.

## 7. 검증과 정리 상태

- 서버 기존 9개 + 배치 도구 6개, **총 15개 회귀 테스트 통과**.
- 임시 배포 TypeScript strict 타입 검사 통과. 이번에 앱 코드는 변경하지 않아 앱 빌드를 다시 실행하지 않았다.
- 운영 `image-signed-urls`는 v2 / 기존 배포 해시 유지, 로컬 원본 4모듈 해시도 실험 전과 같다.
- 임시 함수 `image-url-benchmark-f7003c2e` 삭제는 로컬 CLI 인증 부재로 실행되지 않았다.
  대신 연결된 배포 도구로 **항상 HTTP 410을 반환하는 코드만 남겼고**, 실제 410 응답과 배포 소스를 확인했다.
  현재 버전은 Storage·Redis 호출을 수행하지 않는다. 함수 항목 자체는 목록에 남아 있으므로 삭제 완료로 보고하지 않는다.
- 임시 인증 설정·배포 원본은 로컬에서 정리했다. 실험 캐시 값은 앱과 별도 namespace이며
  마지막 저장 뒤 최대 약 240초 내 만료하도록 설정됐다. 앱 캐시 초기화·정책·유료 플랜 변경은 없었다.

## 8. 포트폴리오에 쓸 수 있는 표현

> Supabase 이미지 링크 발급에 서버 공유 캐시를 구현한 뒤, 기본 배치 API 및 Redis 없는 Edge 배치와
> 동일 입력·권한·유효 기간으로 비교했다. 리뷰 20개·고유 이미지 22개의 HTTP 벤치마크 각 30회에서
> 기본 배치 p50 208ms, Edge 배치 318ms, Redis 100% 적중 685ms를 확인했다.
> 캐시 적중에도 이미지별 권한 조회가 남는 비용을 확인해, Redis 유지보다 기본 배치 적용을 권고했다.

실제 앱 전환 전에는 “운영 앱을 69.7% 개선했다”, “Disk IO를 줄였다”, “Redis를 제거했다”고 쓰지 않는다.
기술 도입의 장점뿐 아니라 **반증 가능한 대안 비교로 불필요한 복잡성을 판단했다**는 사례로 설명할 수 있다.
