# Menu Refresh

최신 원본과 운영 메뉴를 대조해 확인된 변경을 바로 반영하고, 실제로 선택이 필요한 항목만 보류한다. 사용자가 지정한 날짜·매장·수량·모델과 기존 승인을 유지한다.

## 시작과 기준 문서

먼저 Ramap 저장소의 `AGENTS.md`와 [메뉴 등록 정책](../../docs/menu-registration-policy.md)을 읽는다. 공통 판정과 매장별 사용자 결정은 이 정책이 소유한다. 스킬 설치 위치가 달라도 저장소 파일은 작업 중인 Ramap 루트에서 찾는다. 작업 진입점은 `tools/menu-refresh/SKILL.md`다.

재사용 파일의 위치는 `tools/menu-refresh/`다. 다음 작업은 이 폴더의 실행 코드·템플릿·데이터를 직접 재사용한다. 지난 수집 과정의 배치별 코드는 `work-files/manifest.json`의 원래 경로·해시로 찾아 참고하며, 새 실행에는 `scripts/`의 공통 도구를 사용한다. 경로를 전환한 보관본은 현재 해시와 전환 전 원본 해시를 구분한다. 동결된 실행·승인·SQL 결과는 기존 `.artifacts/`에 보존한다.

| 요청 | 읽고 사용할 절차 |
| --- | --- |
| 날짜·매장 목록으로 최신화, 실패 대상 재개 | [실행·수집·복구](references/workflow.md), `refresh_run.py` |
| 기존 보류를 새 규칙으로 점검하거나 체크 승인표 만들기 | [보류 점검·선택 승인](references/pending-review.md), `review_checklist.py` |
| 사용자 체크 선택을 DB에 반영하기 | [선택 결속·반영·목록 갱신](references/pending-review.md#선택을-최신-db에-결속하기) |

원본 수집·완전성 판정에는 `.agents/skills/menu-collect/SKILL.md`와 `menu-collect-review/SKILL.md`, DB 반영 시 `menu-add/SKILL.md`와 사용 가능한 `supabase:supabase`를 함께 적용한다. 단독 메뉴 수집의 읽기 전용 종료 규칙을 최신화 요청 전체에 적용하지 않는다.

## 모델별 역할 분리

DOM 수집은 `.codex/agents/menu-collector.toml`의 **GPT-6 Luna Low**, 반영 판단은 `menu-refresh-judge.toml`의 **GPT-6.1 Sol High**에 맡긴다. 정형 검증·SQL 생성은 공통 스크립트를 재사용하고 DB 쓰기는 주 에이전트가 수행한다. 독립 검토는 별도 `menu_registration_reviewer`의 기존 Sol Medium 설정을 유지한다.

새 작업자는 **`fork_turns="none"`**으로 만들고 역할 설정을 명시한다. 수집자에게는 배정·수집 절차만, 판정자에게는 관련 원문·현재 DB·정책·승인 근거만 전달한다. 긴 원문과 이전 대화는 파일로 인계하고 대화에는 요약·산출물 경로를 반환한다. [작업자 배정·입력 계약·재개](references/agent-workflow.md)를 따른다. 새 모델의 DOM 접근은 실제 확인하고, 주 세션 대체 수집은 실제 수집자와 구분해 기록한다.

## 판정과 자동 반영

판정은 사용자 명시 결정과 적용 중인 제외·보호 기록을 먼저 확인한 뒤 기존 메뉴와 신규 메뉴를 구분한다. 다음 표는 등록 정책의 핵심이며 세부 예외와 매장별 결정은 정책 원문을 따른다.

| 상황 | 처리 |
| --- | --- |
| 기존 DB 등록 메뉴 또는 동일한 기존 메뉴 ID로 확정된 항목 | 무조건 라멘 범위. 이름·설명·면 종류로 다시 승인받지 않는다. |
| 신규 메뉴의 검증된 고정 가격이 **8,000원 이하** | 가격만으로 사이드 판정. 명시적 등록 승인·활성 검증 upsert와 기존 메뉴에는 적용하지 않는다. |
| 신규 탄탄면·마제소바·츠케멘·중화소바 본품, 이름이 라멘·멘으로 끝나는 본품 | 신규 가격 기준을 적용한 뒤 자동 범위 승인. 옵션·면 추가·토핑은 본품으로 등록하지 않는다. |
| 같은 메뉴의 검증된 가격·사진·순서 변경 또는 설명 내용 변경 | 승인 대기 없이 즉시 갱신. 실제 설명 문구 변경만으로 보류하지 않는다. |
| 확인된 신규 등록·삭제 근거가 있는 삭제 | 상시 승인으로 바로 반영. 최신 네이버 전체 메뉴에 없는 기존 행은 직접 등록 근거가 있는 메뉴만 보호하고 나머지는 삭제한다. |
| Place ID와 주소가 모두 같은 매장의 이름 변경 | 같은 매장으로 확정해 현재 원본 명칭 반영. 개별 사용자 지정은 우선한다. |
| 가격·구성·정체·판매/노출 상태에 실제 선택이 필요한 경우 | 불확실한 값만 보류하고 확인된 다른 변경은 진행한다. |

가격·순서·추가·근거 있는 삭제·이미지 변경과 같은 메뉴의 설명 변경은 이미 상시 승인됐다. 작업 승인이나 미리보기 승인을 다시 묻지 않는다. 특정 체크 선택만 반영하라는 요청에서는 그 선택 밖의 DB 값과 보류를 함께 해소하지 않는다.

활성 upsert가 확정한 범위를 다시 묻지 않는다. 같은 메뉴의 검증된 최신 가격·사진·설명은 정규 메뉴와 upsert를 한 트랜잭션에서 동기화한다. 원본에 없는 설명·사진을 기존 행에서 지우거나 `featured=false`만으로 대표를 해제하지 않는다. 기존 변동 가격에 숫자를 만들지 않으며 신규 변동·범위 가격 등록은 정확한 원본 표기를 명시적으로 승인받았을 때 `price_krw=NULL`로 처리한다.

원본 부재 삭제의 보호는 **사용자가 직접 등록한 근거를 정확한 매장·메뉴 ID에 연결한 항목만** 인정한다. DB 감사의 `manual_menu_protection_bindings`가 원본이며 `data/manual-menu-protections.json`은 검증된 캐시다. 최신 보호 기록을 읽지 못하면 삭제하지 않는다. 전체 원문·시각·해시에 결속한 `source_absence_review`로 부재를 확인하고, 일반 upsert의 재등록 방지도 같은 트랜잭션에 처리한다. 사후 검증과 독립 검토는 계획의 기대값과 별도로 모든 원본 미대응 행의 직접 등록 근거를 검사한다.

**보호 목록의 누락은 자동 수집의 증명이 아니다.** 모든 삭제 후보는 [삭제 근거 계약](references/workflow.md#원본-부재와-직접-등록-보호)의 메뉴별 등록 경위 조사를 통과해야 한다. 과거 사용자 입력·등록 감사·첨부/업로드 사진·오버라이드와 별칭 단서를 조사해 미해결이면 삭제를 중단한다. 텍스트 목록만으로 전체 원본을 확인했다고 선언하지 않는다. `deletion_guards.py`의 같은 검증을 계획·SQL 생성·사후 검증에 적용하며, 이전 계획을 수정해 재실행하지 않고 새 실행을 만든다.

## 최신화 실행

1. **대상을 고정한다.** 기본 날짜 필드는 `shop_menu_update_timestamps.updated_at`이다. 날짜만 지정하면 Asia/Seoul 해당 날짜 00:00 **이전(`<`)**을 사용하고 NULL은 오래된 날짜로 추정하지 않는다. 기본 대상은 노출 중이며 `menu_snapshot_enabled=true`이고 네이버 출처가 있는 기존 매장이다. 날짜·ID 순으로 제한 수를 선정하며 출처 없는 매장을 임의로 대체하지 않는다. `select-sql --date-field menu|shop|capture`로 명시된 날짜 필드를 선택하고 `refresh_run.py init`으로 목록·정책·코드·사용자 확인을 고정한다.
2. **전체 원본을 한 번 수집한다.** `assignment.json`의 재수집 제외를 먼저 적용한다. 모든 더보기를 펼친 DOM, 실제 원본 ID, 이름·숫자 가격/가격 표기·설명·메뉴 사진·대표 표시·순서를 보존한다. 추천 메뉴 뒤에 일반 목록을 잇고 같은 이름·가격의 추천 중복만 제거한다. 실제 일반 목록의 다중 가격·사진 행은 원본에 남긴다. 원본 ID가 없으면 null을 사용한다. 캡처 방법과 `result.json` 계약은 [실행 문서](references/workflow.md#브라우저-캡처)를 따른다.
3. **도착한 매장부터 진행한다.** `submit`으로 경로·시각·지점·완전성과 DOM 대조를 검사한다. 준비된 매장의 변경 전 DB 조회를 묶고, 반영은 매장별로 수행한다. 수집 배열·선언값만 고쳐 원본 검증을 통과시키지 않는다. 동일 이름·가격·설명·구성·카테고리의 사진/대표 표시 차이는 대표→정보 충실도→첫 등장 기준으로 자동 선택하며 근거를 `duplicate_resolutions`에 남긴다.
4. **최신 DB를 결속해 반영한다.** 매장·섹션·전체/노출 메뉴·활성 오버라이드·제외 기록을 다시 읽고 `prepare`의 계획과 가드 SQL을 사용한다. 매장별 변경·보호 기록·새 원본 스냅샷을 한 트랜잭션에 적용한다. 삭제와 새 수동 확인 삽입은 동일 SQL의 ROLLBACK을 먼저 검사한다. 동시 변경은 해당 매장만 중단한다. 일반 helper의 지원 범위를 넘는 이름 대응·섹션·이벤트·판매 상태·의미상 중복 정리는 정확한 근거를 `menu-add` 절차에 전달한다.
5. **재조회와 독립 검토를 마친다.** 전체 메뉴, `visible_shop_menu_items`, 보호 기록, 스냅샷 ID·출처·해시를 계획과 대조한다. `menu-add` Phase 3의 `menu_registration_reviewer`에게 아직 검토하지 않은 매장만 한 배치로 전달하고 매장별 판정을 받는다. 같은 매장의 수집자·DB 반영자는 독립 검토자가 될 수 없다. 검토 통과 전에는 완료로 표시하지 않는다.

**완료된 매장의 웹 페이지는 반드시 즉시 닫는다.** 수집·추가 확인·독립 검토가 끝난 작업자도 근거를 저장한 뒤 자신의 전용 탭을 닫고 파일로 인계한다. 배치 종료까지 탭을 쌓아 두지 않는다. [탭 종료 절차](references/workflow.md#탭-종료)를 따른다.

원본에 대응하는 보류·재수집 제외 메뉴가 있으면 기존 섹션 순서를 유지한다. 그 밖에는 원본 대상 메뉴에 연속 순번을 부여하고, 직접 등록 근거로 보호한 DB 전용 메뉴만 상대 순서를 유지해 뒤에 둔다. 메뉴별 `source_url`은 명시적 저장 요청이 있을 때만 설정한다. 변경이 없는 매장의 메뉴 갱신일을 임의로 올리지 않으며 원본 확인 시각은 새 스냅샷에 남긴다.

## 보류 점검과 체크 승인표

[보류 점검·선택 승인](references/pending-review.md)에 입력 계약, 생성 명령, 선택 가능한 처리, 승인 결속과 갱신 순서가 있다. `review_checklist.py build`와 `assets/review-checklist.html`을 재사용한다.

- 새 정책을 먼저 적용해 기존 메뉴의 라멘 여부, 설명 단독 변경, 자동 범위 승인, 신규 저가 사이드, 사진만 다른 동일 메뉴를 반복 검토 대상으로 올리지 않는다. 반영 요청이 없는 상태 확인은 DB 변경과 구분한다.
- 매장·메뉴 URL, 기존/원본 이름·가격·설명·사진·노출 상태, 보류 사유와 **승인할 처리**를 보여준다. 실제 원본이 없으면 메뉴 승인 체크를 만들지 않는다.
- 검토 자료·원본 ID·기존 메뉴 ID·정확한 문구·가격을 고정한다. 중복 보류를 묶어도 모든 원래 레코드 ID를 보존하고 화면 행 수와 처리할 보류 건수를 구분한다.
- 체크 상태 저장은 선택 기록이다. 실제 사용자 승인 메시지의 `bundle_id`, `entry_id`, `choice_key`만 `resolve`하고 최신 DB와 대조한다. 해당 화면을 가리키는 명시적 승인도 그대로 적용하며 같은 승인을 다시 묻지 않는다.
- 선택하지 않은 보류는 그대로 유지한다. 과거 자료로 선택했더라도 아직 남은 원래 레코드가 동일한지 확인하며 이미 성공한 처리는 재실행하지 않는다. 완료된 검토 자료는 덮어쓰지 않는다.

## 재수집 제외·재개·속도

사용자가 재수집 제외를 지정한 정확한 매장·메뉴만 제외한다. DB 감사의 `collection_skip_bindings`가 원본이고 `data/collection-skips.json`은 검증된 캐시다. 최신 DB 기록이 우선한다. 전체 원문 DOM은 보존하되 해당 항목의 별도 상세/사진 수집·판정·자동 쓰기·새 보류·승인 항목 생성을 건너뛰고 기존 DB 행과 원래 보류를 유지한다. 체크하지 않았다는 사실만으로 다음 모든 검토의 미선택 항목을 자동 제외하지 않는다. 제외 해제는 사용자 지시와 정확한 DB 감사·캐시 갱신에 결속한다. [재수집 제외 절차](references/workflow.md#재수집-제외)를 따른다.

수집과 판단은 위의 역할 설정으로 분리한다. 지정 수량과 실제 동시 실행 한도를 알리고 매장 중복 없이 슬롯이 비는 대로 배정한다. 작업자는 전용 산출물 폴더와 역할별 읽기 전용 수집/DB 책임을 맡고 공용 스킬·브라우저 탭을 수정하지 않는다. DB 반영은 주 에이전트가 맡는다.

실행기·캡처·DOM 검증·체크 승인표 코드를 배치마다 다시 만들지 않는다. 같은 실행의 완료 매장은 재수집·재반영하지 않고 실패 매장만 원인을 확인해 한 번 재시도한다. 커밋 결과가 불명확하면 스냅샷 ID와 최신 전체 상태로 성공 여부를 먼저 확인한다. 정책·코드 변경은 기존 실행에 섞지 않고 새 실행에서 적용한다. 저장 증거로 판정할 수 있으면 브라우저를 다시 열지 않는다.

## 결과와 확인

매장별 반영·일치·수동 유지·보류·수집 실패와 추가/삭제/가격/설명/사진/순서 변경 수를 구분해 보고한다. 매장명에는 네이버 매장 링크를 붙이고 같은 Place ID의 메뉴 링크를 함께 제공한다. 통합 보류 JSON에도 `naver_place_url`, `menu_url`을 유지한다. 실행 감사·SQL·해시·사후 검증·독립 검토는 실행 산출물에 보존한다.

실행 코드를 바꾼 경우 helper 테스트와 저장 자료의 `replay_run.py`로 검증한다. 같은 코드의 운영 실행마다 테스트·스킬 개발을 반복하지 않는다. `events.jsonl`·`timings.json`에 DB 호출/단계와 로컬 준비 시간을 남기고 DB 단계 시간으로 전체 수집 시간이나 사용자 대기 시간을 추정하지 않는다. 스킬 문서를 수정한 경우 `skill-creator`의 `quick_validate.py`로 구조를 확인한다.
