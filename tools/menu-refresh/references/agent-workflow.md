# 모델별 역할과 제한된 컨텍스트

## 배정

| 단계 | 역할/설정 | 입력과 산출물 |
| --- | --- | --- |
| DOM 수집 | `menu_collector`: `gpt-6-luna` / `low` | assignment·수집 절차 → DOM·원문·실제 수집 증거 |
| 정형 검사 | 공통 스크립트 | 해시·필수값·원문 대응·중복·유효시각 검사 |
| 반영 판단 | `menu_refresh_judge`: `gpt-6.1-sol` / `high` | 수집 근거·현재 DB·승인 → 파생 캡처·계획·가드 SQL |
| DB 반영 | 주 에이전트와 공통 실행기 | 확정 계획 → ROLLBACK/COMMIT·재조회 |
| 독립 검토 | 별도 `menu_registration_reviewer`: 기존 Sol Medium | 원본·실제 반영 결과 → 매장별 독립 판정 |

정확한 모델·추론 설정은 `.codex/agents/`의 역할 TOML이 소유한다. 기존 작업자의 모델이 설정 파일 수정으로 바뀌었다고 간주하지 않는다. 다음 작업은 새 역할로 시작한다. 사용자 지정 모델이 있으면 그 지시를 우선한다.

새 작업자는 `fork_turns="none"`으로 시작한다. 발견 가능한 named role을 사용하고, 현재 세션에서 새 역할이 아직 발견되지 않으면 해당 TOML을 읽어 같은 지시와 명시적 `model`/`reasoning_effort`로 생성한다. 예를 들어 수집자는 `model="gpt-6-luna", reasoning_effort="low"`, 판정자는 `model="gpt-6.1-sol", reasoning_effort="high"`를 지정한다. 작업 이름만으로 모델을 선택하지 않는다.

요청한 매장 수를 고정하고 실제 동시 슬롯 안에서 작업 풀로 배정한다. 독립 검토 슬롯도 확보한다. 설정의 상한과 실제 세션 슬롯·DOM 접근 가능 여부를 구분해 기록한다.

## 수집자 입력과 종료

수집자에게 배정 파일·자신의 산출물 폴더·확정 제외 기록·공통 수집기/브라우저 절차만 전달한다. 전체 대화·지난 배치·DB 전체 상태·정책 문서 전체를 복제하지 않는다. [브라우저 캡처](workflow.md#브라우저-캡처)의 도구와 재시도 경계를 따른다.

수집자는 필터 전 DOM과 실제 공개 상태를 그대로 저장한다. 해시와 원시 행/사진 수, 펼침·로딩·오류 상태를 기록한다. 범위·가격 의미·기존 메뉴 대응과 주소 정체의 최종 판단, `scope`, `identity_verified`, `quality.passed`는 판정자가 맡는다. 실제 수집 오류는 그대로 남긴다.

모든 역할은 [탭 종료 절차](workflow.md#탭-종료)를 따른다. 수집자는 원문 저장 직후, 추가 확인자와 독립 검토자는 확인 직후 전용 탭을 닫아 파일로 인계한다. 완료된 매장의 페이지를 남겨 두지 않는다.

작업자 DOM 접근이 실패하면 진단 결과를 기록하고 허용된 범위에서만 복구한다. 주 세션만 DOM을 사용할 수 있으면 주 세션이 동일 공통 수집기로 대체 수집하고 실제 수집자를 주 세션으로 기록한다. Luna는 그 파일을 인수·정리할 수 있지만 직접 수집 성공으로 세지 않는다. 모델 변경만으로 도구 접근이 해결됐다고 보고하지 않는다.

## 판정자 입력과 인계

판정자에게는 배정 목록, 관련 수집 파일, 해당 매장의 최신 DB 상태, 정책 경로와 실제 승인/보호/제외 근거만 전달한다. 이미 완료된 매장과 과거 배치의 원문을 다시 넘기지 않는다. 일반적으로 준비된 매장 10~20곳을 묶고 작업 규모에 맞춰 조절한다.

판정자는 공통 파서로 필터 전 canonical 목록과 원문을 대조하고, 품질·정체 근거와 `scope`를 파생 캡처에 결속한다. [result.json 계약](workflow.md#resultjson-계약)을 만족한 뒤 공통 준비 도구로 계획을 만든다. 정형 비교는 스크립트로 실행하고, 변경·보류의 의미를 판단한다. 실패·불확실성에는 근거와 필요한 선택을 남긴다. 고추론 작업이 필요하면 해당 예외만 총괄에게 인계하며 Ultra로 전체 배치를 자동 승격하지 않는다.

수집 파일은 동결한 채 파생 파일을 별도로 만든다. 같은 폴더를 함께 쓰는 경우에도 수집자는 원문, 판정자는 새 candidate/plan/handoff만 소유한다. 판정자는 DB 읽기만 수행하며 쓰기와 `submit`은 주 에이전트가 수행한다.

일반 인계는 `ready` 배열로 전달한다. 각 항목은 `shop_id`, `candidate`, `plan`, `frozen_hashes`와 변경/보류 요약을 담으며 파일 참조는 `{path, sha256, bytes}` 형식을 쓴다. 대화에는 처리 수·오류·인계 파일 경로만 반환한다. 큰 DOM·JSON·SQL·반복 해시 목록은 파일로 전달하고, 총괄도 필요한 요약과 실패 출력만 읽는다.

## 이어서 실행하기

기존 성공 커밋·검증·독립 판정과 동결된 원본/승인을 먼저 확인한다. 미완료 항목만 다음 작업에 배정하며, 현재 버전의 정책·코드 해시와 기존 실행의 해시가 다르면 기존 manifest/context를 바꾸지 않는다. 새 후속 실행을 만들고 원래 실행/매장/캡처 경로·해시·실제 수집자·원시각을 인계 기록에 결속한다. 아직 유효하고 완전한 캡처는 재사용하고, 만료되거나 불완전한 대상만 재수집한다.

새 실행의 `submit`도 원문 포함 경로·완전성·시각·정체와 현재 DB 가드를 검사한다. 예전 작업자의 결과를 새 모델이 직접 수집·검토한 결과로 바꾸거나, 이미 성공한 SQL을 다시 실행하지 않는다. 독립 검토는 수집자·판정자·DB 작성자와 다른 작업자가 수행하며 기존 필수 사진 재확인 규칙을 유지한다.
