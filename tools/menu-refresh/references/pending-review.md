# 보류 점검과 선택 승인표

등록 기준은 Ramap의 `docs/menu-registration-policy.md`를 따른다. 이 문서는 남은 보류를 검토 자료로 고정하고 사용자 선택만 반영하는 절차다. 일반 최신화의 수집·가드 SQL·실행기는 [workflow.md](workflow.md)를 함께 사용한다.

## 표를 만들기 전에

현재 통합 보류 JSON과 실제 DB 상태, 해당 보류에 연결된 원본 스냅샷을 읽는다. 보류에 적힌 과거 사유만 보고 같은 판정을 반복하지 않는다.

| 점검 결과 | 표 생성 전 처리 |
| --- | --- |
| 기존 등록 메뉴의 라멘 여부만 미확정 | 라멘으로 확정. 메뉴 정체·가격·판매 상태의 실제 불확실성만 남긴다. |
| 같은 메뉴의 실제 설명 내용만 변경 | 원본 설명으로 자동 갱신. 과거의 정확한 설명 동등성 결정은 유지한다. |
| 신규 고정 가격 8,000원 이하 | 사이드 판정. 기존 메뉴·명시적 등록 승인·활성 검증 upsert 예외를 적용한다. |
| 자동 승인 유형의 신규 본품 | 가격과 정체가 확인되면 범위 보류 해제. 신규 저가 기준이 우선한다. |
| 동일 구성에서 사진/대표 표시만 다른 원본 중복 | 정책의 대표→정보 충실도→첫 등장 기준으로 자동 선택한다. |
| 이미 성공한 승인 처리 | 성공 감사·사후 상태로 확인하고 다음 반영 대상에서 뺀다. |
| 활성 재수집 제외 | 원래 보류와 DB 행을 유지하고 새 체크 승인 항목을 만들지 않는다. |
| 실제 다중 가격·별도 구성·기존 ID 대응·판매/노출 상태가 불명확 | 값과 근거를 보류에 남기고 선택할 처리를 만든다. |
| 원본 확인 실패 | 매장/메뉴 URL과 실패 사유만 표시한다. 메뉴 등록 승인을 만들지 않는다. |

사용자가 상태 확인본만 요청하면 DB 쓰기를 수행하지 않고 자동 처리 가능한 결과를 구분해 보고한다. 반영을 지시했거나 진행 중인 최신화의 상시 승인 범위라면 확인된 변경을 바로 반영한다. 특정 체크 선택 외의 보류를 유지하라는 배치에서는 미선택 레코드와 DB 값을 변경하지 않는다.

정책 재점검 결과의 과거 스냅샷은 보존하고 현재 목록은 따로 갱신한다. `historical_reason`을 사용할 때에는 과거 사유와 현재 미확정 값을 구분한다. 전체 보류 자료에 남아 있는 재수집 제외 항목은 보고서에서 별도로 표시하며 새 승인표 입력에는 포함하지 않는다. 해당 항목의 재검토를 사용자가 명시한 경우 정확한 제외 해제부터 처리한다.

## 동결 입력 계약

실행별 새 폴더에 다음 파일을 준비한다. 이전 `approval-registry.json`이나 이미 표시한 HTML을 덮어쓰지 않는다.

- `pending.json`: 표에 표시할 현재 보류 레코드 배열. `kind`, `review_kind`, `shop_id`, `shop_name`, `name`, `reason`, `naver_place_url`, `menu_url`을 보존한다. 메뉴 보류에는 `snapshot_id`가 필요하며 기존 ID 대응 후보가 있으면 `candidates`에 실제 기존 이름을 둔다.
- `evidence.json`: `state`와 `snapshots`. `state`에는 `shops`, `items`, `visible` 배열이 필요하고 실제 DB 행을 담는다. `items`에는 섹션 JOIN으로 확인한 `shop_id`를 붙인다. `visible`은 전체 메뉴와 별도로 조회한 최종 노출 상태다.
- `snapshots`: 필요한 실제 원본 스냅샷 배열. 각 행에 `id`, `shop_id`, `source_hash`, `captured_at`, 전체 `menu_items`를 보존한다. 각 메뉴의 실제 `source_id` 또는 null, 이름, 가격/가격 표기, 설명, 사진, 대표 표시를 바꾸지 않는다.

```json
{
  "state": {"shops": [], "items": [], "visible": []},
  "snapshots": [
    {"id": "snapshot UUID", "shop_id": "shop UUID", "source_hash": "검증된 해시",
     "captured_at": "timezone이 있는 원본 확인 시각", "menu_items": []}
  ]
}
```

`state-sql`의 CLI 응답이 `{"rows":[{"state":{...}}]}`라면 내부 `state`를 꺼내 위 계약에 넣는다. 이 예시는 구조 설명이며 빈 배열로 실제 승인표를 만들지 않는다. 스냅샷과 매장 ID가 다르거나 보류 이름에 대응하는 원본 메뉴가 없으면 생성기는 거부한다. 같은 이름의 모든 실제 원본 변형은 보존한다. 수집·DOM 대조가 불완전하면 증거를 먼저 보완하고 승인으로 원본 부재를 대신하지 않는다.

생성기는 보류 레코드 전체 값의 SHA-256 앞 24자를 원래 레코드 ID로 사용한다. `duplicate_values`만 같은 매장·정규화 이름·스냅샷 단위로 묶고 모든 원래 레코드와 ID를 유지한다. 이름이 비슷하다는 이유로 다른 매장이나 다른 스냅샷의 보류를 합치지 않는다.

## 체크 승인표 생성과 표시

Ramap 루트에서 새 경로를 지정한다. HTML 출력은 사용 환경의 허용된 시각화 디렉터리 안에 둔다.

```bash
python3 tools/menu-refresh/scripts/review_checklist.py build \
  --pending <review-dir>/pending.json \
  --evidence <review-dir>/evidence.json \
  --registry <review-dir>/approval-registry.json \
  --output <visualization-dir>/menu-review.html
```

명령은 `assets/review-checklist.html`에 데이터를 주입하고 `bundle_id`·건수·출력 경로를 반환한다. DB 호출은 하지 않는다. 레지스트리나 HTML이 이미 있으면 다른 경로를 요구한다. 생성 전에 모든 경로가 실제 저장 대상인지 확인한다.

표시할 때에는 사용 가능한 `visualize:visualize` 스킬을 읽고 HTML 조각을 대화의 인터랙티브 시각화로 표시한다. 기존 템플릿의 매장/메뉴 링크, 기존/원본 값 비교, 사진 링크, 처리 선택, 체크박스, 페이지 이동, 선택 요약과 승인 버튼을 재사용한다. 기본 페이지 크기는 10행이며 전체 체크는 자동 선택하지 않는다. 기본 처리값이 있어도 체크되지 않은 행은 승인 대상이 아니다.

| 표에 담을 값 | 표시 목적 |
| --- | --- |
| 매장명·주소·네이버 매장 URL·메뉴 URL | 사용자가 지점과 원본을 바로 확인한다. |
| 기존 DB 이름·가격·설명·사진·현재 노출 여부 | 무엇을 바꾸거나 유지할지 확인한다. |
| 원본 이름·가격/가격 표기·설명·사진 | 승인할 실제 원본 값을 확인한다. |
| 현재 보류 사유·확정된 라멘 범위·선택 가능한 처리 | 범위 재검증과 실제 선택 문제를 구분한다. |
| 체크 및 처리 선택, 선택한 보류 건수 | 현재 선택에 포함되는 변경을 명확히 한다. |

`entries`는 화면 행 수이고 `pending_records`는 원래 보류 건수다. 한 행에 중복 보류 2건이 묶이면 선택 수는 2건으로 계산한다. 선택 결과를 보고할 때 이 두 수를 혼용하지 않는다.

## 지원하는 선택과 반영 경로

생성기는 아래 `review_kind`에 따라 가능한 처리를 만든다. 데이터가 단일 원본/단일 기존 행 조건을 만족하지 않으면 선택을 만들어내지 않으며 해당 항목을 보류한다. 필요한 새 처리가 기존 표에 없으면 새로운 검토 자료로 정확한 선택을 제시한다.

| `review_kind` | 화면에서 선택 가능한 처리 | 선택 후 실행할 작업 |
| --- | --- | --- |
| `registration_scope` | 라멘 본품으로 등록 | 정확한 원본 항목을 등록한다. 기존 등록 메뉴를 이 유형으로 다시 검토하지 않는다. |
| `identity_mapping` | 같은 메뉴로 갱신 / 별도의 신규 메뉴로 등록 | 선택한 기존 ID를 유지해 갱신하거나 별도 등록한다. |
| `duplicate_values` | 원본 변형 하나 적용 | 선택된 원본 키의 가격·설명·사진·이름을 사용한다. 다른 원본 행을 스냅샷에서 지우지 않는다. |
| `visibility_event` | 현재 노출 유지 / 상시 노출 / 숨김 | 선택한 노출 처리만 수행하며 이벤트를 추정하거나 생성하지 않는다. |
| `sale_status` | 기존 판매 유지 / 판매 종료로 숨김, 또는 신규 등록 / 제외 | 기존 행은 선택한 판매 상태로, 미등록 후보는 선택한 등록 여부로 처리한다. |
| `price_unknown` | 원본 가격 승인 / 원본 가격 표기 그대로 등록 | 실제 고정 가격 또는 명시적으로 승인된 정확한 변동·범위 표기를 사용한다. |
| `description_change` | 원본 설명으로 변경 | 과거 동결 승인표와의 호환용. 새 설명 단독 변경은 자동 갱신하므로 표에 올리지 않는다. |
| 원본 실패 또는 지원되지 않는 유형 | 승인 체크 없음 | 근거 부재/미확정 상태를 보고하고 유지한다. |

`review_checklist.py resolve`는 선택 결속과 추출만 한다. DB 적용 명령이 아니다. 일반 helper가 지원하는 고정 가격 신규 등록·범위 확인·설명 변경은 실행기의 별도 루트 확인/설명 승인 입력에 연결한다. 수집 결과에 임의의 승인 필드를 넣지 않는다. 이름 대응·사용자 선택 원본 변형·노출/판매 상태·신규 변동 가격처럼 일반 helper가 처리하지 못하는 작업은 `menu-add`의 매장별 가드 트랜잭션으로 수행한다. 이미 받은 정확한 선택을 다시 승인받지 않는다.

신규 변동·범위 가격을 등록 승인받으면 `price_krw=NULL`, `price_text`는 동결한 원본 그대로 저장한다. 0원이나 범위의 최솟값을 만들지 않는다. 숫자가 필요한 upsert 제약을 바꾸지 않으며 해당 범위 확인은 정확한 항목과 트랜잭션 감사에 결속한다. 고정 가격 범위 확인은 활성 `admin_verified` upsert를 통해 재검증을 막는다.

## 실제 사용자 승인 받기

템플릿의 승인 버튼은 다음 형태의 선택과 화면에 표시된 처리 목록을 실제 사용자 메시지로 준비한다.

```json
{
  "bundle_id": "표 생성 시 반환된 SHA-256",
  "selected": [
    {"entry_id": "화면 항목 ID", "choice_key": "선택한 처리 키"}
  ]
}
```

`setWidgetState`로 저장된 체크 상태, `selection_only`, 도구 호출의 `state_only` 입력, 에이전트가 생성한 승인 문구는 승인 권한이 아니다. 실제 사용자 메시지를 근거로 선택 데이터와 승인을 함께 저장한다. 사용자 메시지가 해당 화면과 선택에 결속돼 있으면 “응 반영해”처럼 짧은 승인도 적용하며 재확인을 요구하지 않는다. 어떤 검토 자료와 선택인지 연결할 수 없을 때만 필요한 정보를 확인한다.

실제 사용자 메시지의 선택을 `selection.json`에 저장하고 다음 명령으로 추출한다.

```bash
python3 tools/menu-refresh/scripts/review_checklist.py resolve \
  --registry <review-dir>/approval-registry.json \
  --selection <review-dir>/selection.json \
  --output <review-dir>/resolved-selection.json
```

추출기는 레지스트리 해시·선택의 `bundle_id`, 항목과 처리 키, 중복 선택과 동일 기존 ID에 대한 충돌을 검사한다. 표시하지 않은 처리를 삽입하거나 다른 자료로 선택을 바꾸면 거부한다. 출력에는 선택한 원래 레코드 ID·값, 원본 항목, 기존 DB 가드와 처리만 들어간다. 이 출력 자체에는 승인 권한이 없으므로 실제 인간 지시는 별도의 `authorization.json`에 근거와 범위를 기록한다.

## 선택을 최신 DB에 결속하기

1. **현재 보류를 다시 읽는다.** 선택한 모든 원래 레코드의 ID와 전체 값이 현재 목록에 동일하게 남아 있는지 대조한다. 과거 자료의 전체 보류 해시가 현재 목록과 다르더라도 다른 선택이 먼저 완료된 것일 수 있으므로 선택된 레코드별로 확인한다. 이미 완료된 항목은 성공 감사·DB 상태를 확인해 건너뛴다. 사라진 항목의 처리 내역을 확인할 수 없으면 승인으로 새 작업을 만들지 않는다.
2. **결속 값을 확인한다.** `bundle_id`, 원래 보류 ID, 매장 ID, 스냅샷 ID·해시, 실제 원본 ID 또는 null, 정확한 이름·문구·숫자 가격/가격 표기, 선택한 기존 메뉴 ID를 계획에 넣는다. 행 순번을 원본 ID로 만들거나 이름이 비슷한 다른 메뉴로 선택을 옮기지 않는다.
3. **최신 DB를 읽는다.** 대상 매장·섹션·전체/노출 메뉴·활성 오버라이드·제외 기록을 묶어 조회한다. 선택된 `existing_guard`의 정체와 승인에 관계된 값을 최신 DB와 비교한다. 신규 등록도 같은 정규화 이름의 기존 행과 보호 충돌을 검사한다. 원본이 오래됐거나 불완전하면 선택 대상의 증거만 보완한다. 승인한 가격·문구·정체가 달라졌으면 영향받은 항목만 새 자료로 제시한다.
4. **정확한 선택만 계획한다.** `register_source_menu`, `match_existing_menu`, `choose_source_variant`, 설명·가격·판매·노출 처리를 위 표의 경로로 전달한다. 유지 선택은 현재 상태를 보존한다. 신규 제외 선택은 해당 후보의 등록을 막는 것이며 기존 메뉴 일괄 삭제나 재수집 제외를 뜻하지 않는다. 미선택 보류에 대한 라멘 재검증·자동 보정·새 승인 생성을 추가하지 않는다.
5. **매장별로 반영한다.** 라이브 비교 가드·잠금·처리 수·변경 후 전체 기대 상태와 감사 기록을 한 트랜잭션에 둔다. 새 수동 확인과 삭제는 동일 SQL로 ROLLBACK 검증을 먼저 한다. 성공 또는 커밋 결과 불명확 작업은 같은 SQL을 다시 실행하지 않는다. 감사/스냅샷과 현재 상태로 성공 여부를 확인한 뒤 실패 대상만 진단한다.
6. **사후 검증과 독립 검토를 받는다.** 실제 전체/노출 메뉴·보호 기록·스냅샷을 기대 상태와 대조하고 미선택 범위의 불변성과 직접 등록 근거로 보호한 DB 전용 행을 검사한다. 원본 부재 행을 일괄 보존하지 않으며 보호 근거 없는 잔존 행은 실패다. `menu-add` Phase 3에 따라 매장별 독립 판정까지 받은 뒤 성공 처리로 집계한다.

같은 메뉴의 정확한 설명 승인은 별도 루트 `description_approvals`에 메뉴 ID·원본 ID·기존/원본 문구·`authority=human_user`와 근거를 결속한다. 일반 설명 자동 갱신은 `description_updates_by_policy`로 기록하고 특정 설명 동등성 결정은 `description_equivalences`로 구분한다. 과거 설명 승인이나 동등성 결정을 다른 문구에 확대하지 않는다.

## 반영 결과와 통합 보류 목록 갱신

성공한 **원래 보류 레코드 ID**만 현재 통합 목록에서 뺀다. 화면 항목 수·선택 보류 건수·실제 성공/유지/실패 건수를 별도로 기록한다. 동일 항목에 대한 이미 완료된 승인은 중복 실행하지 않고 그 사실을 보고한다. 미선택과 실패 항목은 그대로 유지한다.

`report.md`, `summary.json`, `verification.json`, 독립 검토 결과에 반영 수·추가/명칭/설명/가격/사진/판매·노출/순서 변경과 유지 상태를 기록한다. 실제 변경이 없었던 유지 선택을 가격 변경처럼 집계하지 않는다. 통합 보류 JSON/Markdown과 현재 상태를 참조하는 복사본을 함께 갱신하며, 완료된 과거 실행 자료와 표시한 `approval-registry.json`은 그대로 보존한다. 모든 매장에는 네이버 매장 URL과 메뉴 URL을 붙인다.

잔여 건수와 각 원래 레코드 값·순서가 기대와 일치하는지 확인한다. 다음 검토가 필요하면 **남은 검토 대상만** 새로운 레지스트리/HTML로 생성한다. 원본 실패·재수집 제외는 별도 상태로 보고하고 새 승인 대상으로 재생성하지 않는다.

## 미선택 항목의 다음 수집 제외

미선택 보류 유지는 기본 동작이다. 다음 수집 제외는 그 범위에 대한 사용자의 명시적 요청이 있을 때 추가한다. 이미 요청받은 제외를 다시 승인받지는 않는다. 현재 적용 중인 정확한 기록은 `data/collection-skips.json`과 최신 DB 감사에서 읽으며 매장/브랜드 공통 제외로 확대하지 않는다.

제외 기록은 실제 사용자 지시와 `bundle_id`, 항목/원래 보류 ID, 매장 ID, 실제 `source_ids` 또는 정확한 `normalized_names`를 결속한다. DB `shop_menu_validation_runs.details.collection_skip_authority=human_user`와 `collection_skip_bindings`에 남긴 뒤 검증된 캐시를 갱신한다. 메뉴와 매장 전체 제외를 구분하며 기존 메뉴 삭제·숨김·`suppress`로 구현하지 않는다. 사용자 요청으로 제외를 해제할 때도 같은 ID의 최신 감사 상태와 캐시를 함께 갱신한다.

세부 데이터 계약과 수집 배정·가드는 [workflow.md의 재수집 제외](workflow.md#재수집-제외)를 따른다. 전체 원문 DOM은 유지하되 제외 메뉴의 별도 상세 수집·범위 재판정·자동 갱신·새 보류·새 체크 승인 항목은 건너뛴다.
