# Event Add

Turn one manually supplied Instagram post, reel, or story/screenshot into one or more verified `public.shop_events` rows.

Read `AGENTS.md` and `.codex/commands/event-add.md`. The command requires a readable information-sharing preview: preserve verifiable event details while reorganizing the description into clear paragraphs. Apply the available `supabase:supabase` skill for schema access and authenticated writes. The primary agent owns recognition, preview, and approved registration; this workflow does not invoke a product-code implementer.

## Invocation

- `/event-add <instagram-url>`
- A bare Instagram post or reel URL when the conversation is about recognizing or adding an event
- A manual event request with a shop name and story/screenshot when no story URL exists

Treat a URL-only request as recognition intent. Start immediately without asking the user to restate the task.

## Phase 1: Recognize and Preview

1. Canonicalize a supplied Instagram URL by removing query parameters and fragments and retaining one trailing slash. If no event URL is supplied, resolve the shop first and use that shop's `public.ramen_shops.instagram_url` as the fallback `source_url`; canonicalize it the same way. Never invent another URL. Mark the preview and stored record as using a shop-profile fallback.
2. Open the post in an available signed-in browser. Read the full caption and every relevant carousel image. For the caption, prefer raw page metadata or structured page data when available; do not reconstruct it manually from DOM text nodes. Never bypass a private, deleted, or inaccessible post; ask for the caption or screenshots instead.
3. Extract the event category (`collab`, `popup`, `limited_menu`, `summer_limited`, `new_menu`, or `store_renewal`), title, description, start date, and end date. Use ISO `YYYY-MM-DD`. Do not guess ambiguous dates. Use the same start and end date for a clearly single-day event. Use `new_menu` for a newly launched regular menu, and `limited_menu` or `summer_limited` for menus with an announced end date. For `store_renewal`, set `end_date` to `null`; it is displayed and scheduled only on `start_date`.
4. Keep the original caption as source evidence, then reorganize its verified event information into a readable Korean description under `.codex/commands/event-add.md`. Preserve dates, prices, quantities, menu names, conditions, and other material details; do not invent, exaggerate, or silently omit them. Put venue/location and reservation or waiting details in their separately previewed fields when the schema supports them. Facts visible only in carousel images must have explicit image evidence and be identified in the preview. If the user requests verbatim caption storage, preserve the requested wording and line breaks instead. The preview must show the exact final description that will be stored; keep any existing raw-source row unchanged.
5. Resolve the configured Ramap project without printing `local.properties` credentials, inspect the current schema through an authenticated MCP or linked CLI path, and identify the shop using the posting account, caption shop name, and `public.ramen_shops.instagram_url`.
6. Ask the user to choose when multiple shops match. Stop and report the missing prerequisite when no shop exists.
7. Check duplicates against `source_url`, `title`, `start_date`, and the actual venue identity used by the current schema and `supabase/functions/register-event/index.ts`. For a registered venue, match its `shop_id`; for an external venue, match `shop_id IS NULL` and its resolved `external_venue_id`. The posting shop's participant ID is not the external event's venue ID. Report an existing row instead of proposing a duplicate. A shop-profile fallback may be reused for different event titles or dates.
8. For an external venue, explicitly ask for its Instagram profile URL, Naver Map URL, and Kakao Map URL separately. Present any links evidenced by the post or an explicitly selected saved venue for confirmation; ask the user to supply or correct the others. Explain that each link is optional: the user may leave any or all empty, and an unconfirmed or omitted link remains `null` without blocking registration. Never guess a URL or copy the participating shop's link to the external venue.
9. Show a preview with participant shop id/name, inferred category, the exact description that will be stored, separately extracted venue/address, all three external-venue link values (including `null`), the public Instagram profile-image candidate or its unavailability when an external-venue Instagram URL is confirmed, separately extracted waiting or reservation information, date range, up to five ordered carousel image candidates, canonical source URL, and whether it is the shop-profile fallback. A registered venue stores `shop_id`. For an external venue, look up reusable `external_venues`: use an explicitly selected matching id when the identity is known, otherwise preview it as a new venue; never merge automatically by name. The event retains nonblank `venue_name` and only confirmed link snapshots while its `shop_id` is null. Never add an external venue as a participant. Display the final description's intended paragraphs faithfully; for a user-requested verbatim caption, use a code block if needed. Mention material uncertainty or unavailable carousel content separately. Do not add the supplied PNG files to the repository.
10. Stop after showing the preview and wait for the user's explicit approval. Do not register merely because recognition succeeded or because the user supplied the URL. If the user requests corrections, apply them and show a revised preview before asking again. Treat approval as applying only to the latest preview.

Do not write any database row during Phase 1.

## Phase 2: Register and Verify

1. Continue only after an explicit confirmation such as `등록해줘`, `진행해`, or `확인` referring to the latest preview. A confirmation is required for every registration; there is no automatic or implicit registration path.
2. Recheck the previewed event identity and resolved venue immediately before insertion, including external-venue events and shop-profile fallback URLs. Reuse an existing exact match rather than replaying a successful registration after a partial failure.
3. Insert each distinct event into `public.shop_events`. For an external venue, leave `shop_id` null, reference the selected or newly created `external_venues.id`, and retain `venue_name` plus only user-confirmed canonical Instagram profile, Naver Map, and Kakao Map URLs as nullable event snapshots; save the posting/participating registered shop only in `shop_event_participants`. Do not auto-merge ambiguous places by name. For a registered venue, keep the external reference and all external venue links null. A post with separate date ranges may produce multiple rows in one confirmed batch.
4. If the selected or newly created external venue has an Instagram URL but no `image_path`, fetch that public profile's `og:image`. Accept only an HTTPS image on `cdninstagram.com` or its subdomains, then verify JPEG/PNG/WebP MIME type, actual file type, and a 10 MiB size limit. Upload it to the public `shop-profile-images` bucket under `venues/<external_venue_id>.<ext>` using the authenticated Supabase CLI, verify the object and HTTP 200 public URL, then save only that relative path to `external_venues.image_path`. Keep an existing path; never replace it implicitly. If the profile or upload is unavailable, leave `image_path` null and report the reason without failing the approved event registration. The app already resolves this path for the external-venue image in event details.
5. Inspect the live schema and Storage bucket before handling event images. If the approved schema exposes `image_paths` and the public `event-images` bucket is available, upload only the confirmed carousel images under an event-scoped path, retain at most five ordered relative paths, and insert those paths. Preserve the confirmed image files byte-for-byte: do not center-crop, force a square aspect ratio, resize into a thumbnail, or substitute a search result, social-media preview, or other derivative for the confirmed carousel image. Before upload, inspect each candidate's actual file type, byte size, pixel dimensions, and aspect ratio. Compare its aspect ratio and visible content with the confirmed carousel image; reject a candidate that has been cropped or whose full-frame fidelity cannot be established, and stop to report the issue rather than saving it. Prefer the authenticated Supabase CLI (`supabase storage cp`) for uploads; discover current flags with `supabase storage cp --help`, use a linked project or temporary CLI workdir, and do not use an `anon` REST upload when the authenticated CLI is available. After upload, verify each object's bytes or image dimensions/aspect ratio match the local confirmed candidate, that the object exists, and that its public URL returns HTTP 200 before saving the relative path. Store only relative public paths in `image_paths`; the app constructs the public URL. If the column, bucket, or authenticated upload prerequisite is unavailable, report the prerequisite instead of inventing URLs or writing image bytes elsewhere. Never add the actual PNG files to the repository.
6. Insert only columns that exist in the inspected schema and store the approved description exactly as previewed. Store extracted waiting information only in matching schema columns such as `waiting_method` and `waiting_url`; do not put it back into `description`. Treat the inferred category as preview metadata when `shop_events` has no `type` column.
7. Select every inserted row by id and verify its description, venue, participants, dates, waiting fields, source URL, and image paths against the approved preview. Report the verified shop, title, date range, source URL, event id, external-venue profile-image path or skip reason, and ordered event image paths when present.

Never expose or place a service-role key in app code. Never write before confirmation.
